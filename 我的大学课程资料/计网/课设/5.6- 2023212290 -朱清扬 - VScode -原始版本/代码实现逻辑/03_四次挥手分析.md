# TCP四次挥手分析 - 算法实现逻辑

## 一、TCP四次挥手概述

TCP四次挥手（Four-Way Handshake）是TCP释放连接的标准机制。由于TCP是**全双工**协议，每个方向的数据传输需要**独立关闭**，因此需要四次报文交互完成连接释放。

## 二、为什么需要四次挥手？

### 2.1 全双工特性

TCP连接包含两条独立的数据流：
- **A → B**: 客户端向服务器发送数据
- **B → A**: 服务器向客户端发送数据

两条数据流需要**分别关闭**，因此需要两组FIN-ACK交互。

### 2.2 与三次握手的区别

| 阶段 | 三次握手 | 四次挥手 |
|------|----------|----------|
| 原因 | 服务器可以合并SYN和ACK | FIN和ACK不能随意合并 |
| 步骤 | SYN → SYN-ACK → ACK | FIN → ACK → FIN → ACK |
| 合并 | 第二次握手合并了SYN+ACK | 通常不能合并（见2.3） |

### 2.3 为什么不能合并为三次？

```
场景：服务器还有数据要发送

Client                           Server
   │                               │
   ├──────── FIN ─────────────────>│  A关闭发送
   │                               │
   │<─────── ACK ──────────────────┤  B确认
   │                               │
   │<─────── 数据 ─────────────────┤  B还在发送数据！
   │<─────── 数据 ─────────────────┤
   │<─────── 数据 ─────────────────┤
   │                               │
   │<─────── FIN ──────────────────┤  B也关闭发送
   │                               │
   ├──────── ACK ─────────────────>│  A确认
   │                               │
```

当一方发送FIN时，只表示**该方不再发送数据**，但可能还需要接收对方的数据。因此对方需要先ACK确认收到FIN，等自己的数据发送完毕后再发送FIN。

## 三、四次挥手协议流程

### 3.1 详细流程图

```
     主动关闭方 (A)                           被动关闭方 (B)
         │                                        │
         │  状态: ESTABLISHED                     │  状态: ESTABLISHED
         │                                        │
    时刻T1 ├───────────── FIN ─────────────────────>│
         │  Seq = u                               │
         │  Flags = FIN+ACK (0x11)                │
         │                                        │
         │  状态: FIN_WAIT_1                      │  状态: CLOSE_WAIT
         │                                        │
    时刻T2 │<──────────── ACK ──────────────────────┤
         │              Ack = u + 1               │
         │                                        │
         │  状态: FIN_WAIT_2                      │  (B可能继续发送数据)
         │                                        │
         │                ···                     │  (数据传输中)
         │                                        │
    时刻T3 │<──────────── FIN ──────────────────────┤
         │              Seq = v                   │
         │              Flags = FIN+ACK (0x11)    │
         │                                        │
         │  状态: TIME_WAIT                       │  状态: LAST_ACK
         │                                        │
    时刻T4 ├───────────── ACK ─────────────────────>│
         │  Ack = v + 1                           │
         │                                        │
         │  (等待2MSL)                            │  状态: CLOSED
         │                                        │
         │  状态: CLOSED                          │
         │                                        │
```

### 3.2 各步骤详细说明

#### 第一次挥手 (FIN)

**发送方**: 主动关闭方（通常是客户端）
**目的**: 表明不再发送数据，请求关闭

| 字段 | 值 | 说明 |
|------|-----|------|
| 序列号 Seq | u | 当前序列号 |
| 确认号 Ack | - | 可能携带最后的ACK |
| 标志位 Flags | FIN+ACK (0x11) | 结束标志 |

**状态转换**: ESTABLISHED → FIN_WAIT_1

#### 第二次挥手 (ACK)

**发送方**: 被动关闭方
**目的**: 确认收到对方的FIN请求

| 字段 | 值 | 说明 |
|------|-----|------|
| 确认号 Ack | u + 1 | 确认收到FIN（FIN消耗一个序列号） |
| 标志位 Flags | ACK (0x10) | 确认标志 |

**状态转换**:
- 主动方: FIN_WAIT_1 → FIN_WAIT_2
- 被动方: ESTABLISHED → CLOSE_WAIT

#### 第三次挥手 (FIN)

**发送方**: 被动关闭方
**目的**: 表明该方也完成数据发送，请求关闭

| 字段 | 值 | 说明 |
|------|-----|------|
| 序列号 Seq | v | 被动方当前序列号 |
| 标志位 Flags | FIN+ACK (0x11) | 结束标志 |

**状态转换**: CLOSE_WAIT → LAST_ACK

#### 第四次挥手 (ACK)

**发送方**: 主动关闭方
**目的**: 最后确认，完成连接关闭

| 字段 | 值 | 说明 |
|------|-----|------|
| 确认号 Ack | v + 1 | 确认收到对方FIN |
| 标志位 Flags | ACK (0x10) | 确认标志 |

**状态转换**:
- 主动方: FIN_WAIT_2 → TIME_WAIT → (2MSL后) CLOSED
- 被动方: LAST_ACK → CLOSED

## 四、TIME_WAIT状态

### 4.1 为什么需要TIME_WAIT？

TIME_WAIT是主动关闭方在发送最后一个ACK后进入的状态，需要等待2MSL（Maximum Segment Lifetime，最大段生存时间）。

#### 原因1：确保最后的ACK能够到达

```
场景：最后的ACK丢失

Client (TIME_WAIT)                  Server (LAST_ACK)
      │                                 │
      ├─────── ACK ──────────────X      │  ACK丢失
      │                                 │
      │        (超时)                   │
      │<────── FIN ─────────────────────┤  服务器重传FIN
      │                                 │
      ├─────── ACK ────────────────────>│  客户端重发ACK
      │                                 │
```

如果客户端立即进入CLOSED状态，就无法响应服务器重传的FIN。

#### 原因2：让旧连接的报文在网络中消失

```
场景：旧报文干扰新连接

时刻T1: 旧连接A→B关闭
时刻T2: 立即建立新连接A→B（相同端口）
时刻T3: 旧连接的延迟报文到达，被新连接误认为有效数据
```

等待2MSL可以确保旧连接的所有报文都已过期。

### 4.2 MSL值

- **推荐值**: 2分钟（RFC 793）
- **实际实现**: Linux默认30秒，Windows默认120秒
- **2MSL**: 一个方向最大延迟MSL，来回2MSL

## 五、算法实现详解

### 5.1 FIN包检测算法

```python
def analyze_fin(self, conn_id):
    """
    分析TCP四次挥手
    
    算法流程:
    1. 遍历连接的所有数据包
    2. 检测带有FIN标志的数据包
    3. 记录所有FIN包信息
    4. 判断挥手是否完整
    
    参数:
        conn_id: TCP连接标识
        
    返回:
        dict: 包含fin_packets列表和complete标志
        None: 如果未检测到FIN包
    """
    packets = self.get_connection_packets(conn_id)
    
    # 查找所有FIN包
    fin_packets = []
    
    for pkt in packets:
        flags = pkt['flags']
        
        # 检测FIN标志位
        if isinstance(flags, int):
            # FIN标志位在最低位: 0x01
            # 常见组合:
            # - FIN: 0x01
            # - FIN+ACK: 0x11
            # - FIN+ACK+PSH: 0x19
            if flags & 0x01:  # FIN标志位被设置
                fin_packets.append(pkt)
        elif 'F' in str(flags):
            # 字符串形式包含'F'
            fin_packets.append(pkt)
    
    # 完整的四次挥手至少需要2个FIN包
    # （每个方向各一个FIN）
    if len(fin_packets) >= 2:
        return {
            'fin_packets': fin_packets,
            'complete': True
        }
    
    return None
```

### 5.2 FIN标志位检测详解

```python
def is_fin_packet(flags):
    """
    判断是否为FIN包
    
    FIN标志位: 0x01 (二进制最低位)
    
    常见的FIN包标志组合:
    - 0x01 (FIN)
    - 0x11 (FIN+ACK) ← 最常见
    - 0x19 (FIN+ACK+PSH)
    """
    if isinstance(flags, int):
        # 检查最低位是否为1
        return (flags & 0x01) != 0
    elif isinstance(flags, str):
        # 检查字符串是否包含'F'
        return 'F' in flags
    return False

# TCP标志位定义
TCP_FLAGS = {
    'FIN': 0x01,  # Finish - 结束连接
    'SYN': 0x02,  # Synchronize - 同步序列号
    'RST': 0x04,  # Reset - 重置连接
    'PSH': 0x08,  # Push - 推送数据
    'ACK': 0x10,  # Acknowledgment - 确认
    'URG': 0x20,  # Urgent - 紧急指针有效
}

# 常见标志组合
FLAG_COMBINATIONS = {
    0x01: 'FIN',
    0x02: 'SYN',
    0x10: 'ACK',
    0x11: 'FIN-ACK',
    0x12: 'SYN-ACK',
    0x14: 'RST-ACK',
    0x18: 'PSH-ACK',
    0x19: 'FIN-PSH-ACK',
}
```

### 5.3 挥手方向识别

```python
def identify_fin_direction(fin_packets):
    """
    识别四次挥手的方向
    
    返回:
        dict: {
            'initiator': 主动关闭方信息,
            'responder': 被动关闭方信息,
            'first_fin': 第一个FIN包,
            'second_fin': 第二个FIN包
        }
    """
    if len(fin_packets) < 2:
        return None
    
    # 第一个FIN包的发送方是主动关闭方
    first_fin = fin_packets[0]
    initiator = f"{first_fin['src_ip']}:{first_fin['src_port']}"
    
    # 找到另一方发送的FIN包
    second_fin = None
    for fin in fin_packets[1:]:
        sender = f"{fin['src_ip']}:{fin['src_port']}"
        if sender != initiator:
            second_fin = fin
            break
    
    if second_fin:
        responder = f"{second_fin['src_ip']}:{second_fin['src_port']}"
        return {
            'initiator': initiator,
            'responder': responder,
            'first_fin': first_fin,
            'second_fin': second_fin
        }
    
    return None
```

## 七、特殊情况处理

### 7.1 同时关闭（Simultaneous Close）

```
Client                           Server
   │                               │
   ├──────── FIN ─────────────────>│
   │<─────── FIN ──────────────────┤  同时发送
   │                               │
   │  状态: CLOSING                │  状态: CLOSING
   │                               │
   ├──────── ACK ─────────────────>│
   │<─────── ACK ──────────────────┤
   │                               │
   │  状态: TIME_WAIT              │  状态: TIME_WAIT
```

### 7.2 半关闭（Half-Close）

TCP支持半关闭状态，一方关闭了发送方向，但仍可接收数据：

```
Client                           Server
   │                               │
   ├──────── FIN ─────────────────>│  客户端关闭发送
   │<─────── ACK ──────────────────┤
   │                               │
   │  (客户端FIN_WAIT_2)           │  (服务器CLOSE_WAIT)
   │                               │
   │<─────── 数据 ─────────────────┤  服务器仍可发送
   │<─────── 数据 ─────────────────┤
   │                               │
   │<─────── FIN ──────────────────┤  服务器关闭发送
   ├──────── ACK ─────────────────>│
```

### 7.3 RST强制关闭

RST（Reset）可以立即终止连接，无需四次挥手：

```python
def detect_reset(packets):
    """检测RST强制关闭"""
    for pkt in packets:
        flags = pkt['flags']
        if isinstance(flags, int) and (flags & 0x04):
            return pkt
        elif isinstance(flags, str) and 'R' in flags:
            return pkt
    return None
```

## 八、知识点总结

### 8.1 四次挥手核心要点

| 要点 | 说明 |
|------|------|
| FIN标志 | 结束标志，表示发送方不再发送数据 |
| 全双工 | 两个方向独立关闭 |
| TIME_WAIT | 主动关闭方等待2MSL |
| CLOSE_WAIT | 被动关闭方等待上层应用关闭 |
| FIN消耗序列号 | 和SYN一样消耗一个序列号 |

### 8.2 状态转换路径

**主动关闭方**:
```
ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
                         ↘ CLOSING → TIME_WAIT → CLOSED (同时关闭)
```

**被动关闭方**:
```
ESTABLISHED → CLOSE_WAIT → LAST_ACK → CLOSED
```

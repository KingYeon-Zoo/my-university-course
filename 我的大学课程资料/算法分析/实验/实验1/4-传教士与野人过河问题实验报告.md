# 实验一：算法伪代码设计的一般思路

## 题目4：传教士与野人过河问题

## 一、实验内容和要求

本实验要求通过分析小规模具体实例，归纳、提炼并形式化描述传教士与野人过河问题的通用算法步骤，最终产出规范的伪代码描述及设计过程报告。实验需要展示从问题定义、实例手工求解、思路提炼到伪代码撰写的完整思维过程。

## 二、问题背景和相关工作介绍

传教士与野人过河问题是人工智能和状态空间搜索领域的经典问题，最早出现于1800年代的数学娱乐题。该问题是状态空间搜索、广度优先搜索（BFS）和深度优先搜索（DFS）的典型教学案例。

问题定义：有3个传教士和3个野人要过河，只有一条船，船每次最多载2人。在任何时刻（河的两岸以及船上），如果野人数量超过传教士数量，传教士就会被野人吃掉。如何安全地将所有人运送到对岸。

约束条件：
1. 船的容量约束：每次最多载2人，最少1人（船不能自己过河）
2. 安全约束：河两岸以及船上，传教士数量必须大于等于野人数量，或传教士数量为0
3. 目标状态：所有传教士和野人都从左岸到达右岸

输入：左岸传教士数量M，左岸野人数量C，船的容量K

输出：一系列合法的过河动作序列，或判定问题无解

相关工作：该问题可以建模为状态空间搜索问题，通过BFS可以找到最短解。问题的解空间形成一个有向图，每个状态对应图中的一个节点，每个合法动作对应一条边。经典的3传教士3野人问题有解，最短解需要11步。

## 三、解题思路

### 3.1 问题实例化

标准实例：3个传教士，3个野人，船容量为2。

状态表示：使用三元组(m, c, b)表示状态，其中：

1. m：左岸传教士数量（0到3）
2. c：左岸野人数量（0到3）
3. b：船的位置（0表示右岸，1表示左岸）

初始状态：(3, 3, 1)，即3个传教士、3个野人在左岸，船在左岸

目标状态：(0, 0, 0)，即所有人都到右岸，船也在右岸

### 3.3 思路提炼与通用化

核心策略：广度优先搜索（BFS）

1. 状态空间建模：
   - 状态：(m, c, b)，m为左岸传教士数，c为左岸野人数，b为船位置
   - 动作：船上1到K人过河，包括不同的传教士和野人组合
   - 状态转移：根据动作更新状态

2. 安全性检查：
   - 对于岸的某一侧，传教士数量要么为0，要么≥野人数量
   - 动作合法性：人数在有效范围内，且源侧有足够的人

3. 搜索策略：
   - 使用BFS保证找到最短路径
   - 使用访问标记避免重复访问状态
   - 记录父状态和转移动作，用于回溯构造解路径

4. 算法框架：
   - 初始化：将初始状态加入队列
   - 循环：从队列取出状态，生成所有合法后继状态
   - 检查：如果到达目标状态，回溯构造路径
   - 标记：访问过的状态不再重复访问

可扩展性分析：

1. 状态空间大小：(M+1) × (C+1) × 2，对于3传教士3野人，共32个可能状态
2. BFS时间复杂度：O(状态数×分支因子)，分支因子取决于船容量
3. 对于更大规模（如5传教士5野人），状态空间增长但仍可接受
4. 算法保证找到最短解，适合实际应用

## 四、算法伪代码

### 算法1：传教士与野人问题主算法（BFS）

输入：传教士总数M，野人总数C，船容量K

输出：最短过河方案，或判定无解

```
MISSIONARIES-AND-CANNIBALS(M, C, K)
    // 定义初始状态和目标状态
    initialState = (M, C, 1)  // 所有人在左岸，船在左岸
    goalState = (0, 0, 0)  // 所有人在右岸，船在右岸
    
    // 初始化BFS队列和访问标记
    queue = new Queue()
    queue.enqueue(initialState)
    visited = new Set()
    visited.add(initialState)
    parent = new Map()  // 记录状态的父状态
    parent[initialState] = null
    action = new Map()  // 记录转移动作
    
    // BFS主循环
    while not queue.isEmpty()
        currentState = queue.dequeue()
        
        // 检查是否到达目标状态
        if currentState = goalState
            return CONSTRUCT-SOLUTION(parent, action, goalState)
        
        // 生成所有合法后继状态
        successors = GENERATE-SUCCESSORS(currentState, M, C, K)
        
        for each nextState in successors
            if nextState not in visited
                visited.add(nextState)
                parent[nextState] = currentState
                action[nextState] = (nextState, currentState之间的动作)
                queue.enqueue(nextState)
    
    // 队列为空仍未找到解
    return "无解"
```

### 算法2：生成后继状态

输入：当前状态(m, c, b)，总人数M和C，船容量K

输出：所有合法后继状态的列表

```
GENERATE-SUCCESSORS(state, M, C, K)
    (m, c, b) = state  // 解析状态
    successors = new List()
    
    // 确定船的方向：1表示从左到右，-1表示从右到左
    if b = 1  // 船在左岸
        direction = -1
    else  // 船在右岸
        direction = 1
    
    // 枚举所有可能的船上人员组成
    for mis = 0 to K  // 船上传教士数量
        for can = 0 to K - mis  // 船上野人数量
            if mis + can = 0 or mis + can > K
                continue  // 船不能空载或超载
            
            // 计算新状态
            newM = m + direction × mis
            newC = c + direction × can
            newB = 1 - b  // 船到对岸
            
            // 检查新状态的合法性
            if IS-VALID(newM, newC, newB, M, C)
                successors.add((newM, newC, newB))
    
    return successors
```

### 算法3：状态合法性检查

输入：状态(m, c, b)，总人数M和C

输出：状态是否合法（布尔值）

```
IS-VALID(m, c, b, M, C)
    // 检查人数范围
    if m < 0 or m > M or c < 0 or c > C
        return false
    
    // 计算右岸人数
    rightM = M - m
    rightC = C - c
    
    // 检查左岸安全性
    if m > 0 and m < c  // 左岸有传教士但数量少于野人
        return false
    
    // 检查右岸安全性
    if rightM > 0 and rightM < rightC
        return false
    
    return true
```

### 算法4：构造解路径

输入：父状态映射parent，动作映射action，目标状态goal

输出：从初始状态到目标状态的动作序列

```
CONSTRUCT-SOLUTION(parent, action, goal)
    path = new List()
    currentState = goal
    
    // 从目标状态回溯到初始状态
    while parent[currentState] ≠ null
        path.add(action[currentState])
        currentState = parent[currentState]
    
    // 反转路径得到正向序列
    path.reverse()
    
    return path
```

### 算法复杂度分析

时间复杂度：
1. 状态空间大小：O((M+1) × (C+1) × 2) = O(MC)
2. 每个状态的分支因子：最多O(K²)种船上人员组合
3. BFS访问每个状态至多一次：O(MC × K²)
4. 对于M=C=3, K=2：约32个状态，每个最多4种动作，总计约128次操作

空间复杂度：
1. 访问标记：O(MC)
2. BFS队列：最坏情况O(MC)
3. 父状态映射：O(MC)
4. 总空间复杂度：O(MC)

算法特性：
1. 完备性：BFS保证如果有解则一定能找到
2. 最优性：BFS保证找到步数最少的解
3. 时间效率：对于小规模问题（M, C ≤ 10）非常高效
4. 空间效率：需要存储访问过的所有状态

```
(2,2,1) → (2,0,0) → (2,1,1) → (0,1,0) → (1,1,1) → (0,0,0)
```

5步完成。

验证：每步都满足安全约束。

## 七、实验结果分析

通过实验验证，广度优先搜索算法能够有效求解传教士与野人过河问题。

算法正确性分析：
1. 完备性：BFS系统地搜索所有可达状态，如果有解必能找到
2. 最优性：BFS按层次搜索，保证找到步数最少的解
3. 状态去重：通过visited集合避免重复访问，保证效率

性能分析：
1. 对于3传教士3野人问题：
   - 状态空间：4×4×2=32个可能状态
   - 实际可达状态：约16个（很多状态因不安全而不可达）
   - 最短解：11步
   - BFS搜索效率高，几乎是瞬时完成

2. 对于更大规模：
   - 5传教士5野人：6×6×2=72个状态，仍可快速求解
   - 状态空间增长是线性的，算法可扩展性好

实际应用价值：
1. 该问题是状态空间搜索的经典教学案例，帮助理解BFS、状态表示、约束检查等概念
2. 算法框架可推广到其他过河问题、路径规划、谜题求解等领域
3. 展示了如何将实际问题建模为状态空间搜索问题

遇到的问题及解决方案：
1. 问题：初始对安全性约束理解有误，认为"传教士数量≥野人数量"是严格要求
   解决：重新理解题意，当某侧传教士数量为0时，即使有野人也是安全的（因为没有传教士被吃）

2. 问题：手工搜索容易陷入局部路径，难以找到完整解
   解决：采用系统化的BFS方法，按层次搜索，用队列管理待扩展状态

3. 问题：状态表示和转移关系的设计
   解决：使用三元组(m, c, b)简洁地表示状态，通过船的位置b确定转移方向

4. 问题：路径回溯和动作记录
   解决：在搜索过程中维护parent映射和action映射，到达目标后回溯构造完整路径

5. 问题：手工推演时容易计算错误
   解决：建立清晰的表格，每一步都记录左岸、船上、右岸的状态，并逐项检查安全性

改进空间：
1. 对于只需判定是否有解的情况，可以使用深度优先搜索（DFS）节省空间
2. 可以使用双向BFS（从初始和目标同时搜索）进一步提高效率
3. 对于变体问题（如不同的船容量、人数），算法框架不变，只需调整参数

## 八、总结

### 感想、体会、建议

通过本次传教士与野人过河问题的实验，我获得了以下深刻体会：

1. 状态空间搜索的思维模式：这个问题让我学会了如何将一个实际问题抽象为状态空间搜索问题。关键在于：定义状态表示、识别合法动作、建立状态转移关系、设置目标条件。这种建模能力是解决许多AI问题的基础。

2. BFS的威力：广度优先搜索看似简单，但在本问题中展现了强大的能力。它不仅保证找到解，还保证找到最短解。通过手工推演11步的解，我深刻感受到BFS如何系统地、无遗漏地搜索解空间。

3. 约束的重要性：问题的约束（安全性）不仅是限制，更是指导搜索方向的关键信息。通过约束检查，算法可以及时剪掉不可行分支，避免无效搜索。对约束的正确理解直接影响算法的正确性。

4. 手工推演的挑战与价值：在纸上手工模拟BFS搜索过程，让我深刻体会到了算法的每一个细节。特别是状态去重、队列操作、路径回溯等，通过手工操作比单纯看伪代码理解更深刻。

5. 问题规模的影响：3传教士3野人问题只有32个可能状态，手工搜索尚可完成。但如果规模扩大到10传教士10野人，状态空间将达到242个，手工搜索就完全不可行了。这让我认识到算法和计算机的价值。

6. 算法的可扩展性：BFS算法框架非常通用，只需修改状态表示和转移规则，就可以应用到各种过河问题的变体（如狼羊菜过河、不同船容量等）。这种通用性是算法设计追求的目标。

7. 从直觉到形式化：初次接触这个问题时，凭直觉可以想出一些移动策略，但很难保证找到最优解或所有解。通过形式化的状态空间建模和系统化的BFS搜索，问题变得清晰可控。

8. 数据结构的选择：BFS需要队列、访问标记集合、父状态映射等数据结构的支持。合适的数据结构让算法实现变得简洁高效，这再次印证了"算法+数据结构=程序"的重要性。

本次实验让我深刻理解了状态空间搜索的本质，也让我认识到，很多看似复杂的实际问题，只要找到合适的建模方法和搜索策略，就可以用相对简单的算法优雅地解决。BFS作为一种基础但强大的搜索算法，将成为我解决路径规划、谜题求解等问题的重要工具。

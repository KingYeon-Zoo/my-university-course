# 以下是我的实习经历，以下的内容都是真实的，来自于我和同事的复盘对话记录，语言上偏口语。

我的项目是之前在华为实习过的项目：面向医疗的agent，主要用于协助医生就诊，主要是妇科疾病部分 但是由于我是实习生且现在已经实习完毕了不能接触到这个项目，所以无法给出明确的数据。并且这些医疗数据是有隐私的，我们当时开发都签署了隐私协议。但是我可以说下我的实习经历，也就是开发中遇到的困难，过程。
我的项目是政府，医院，华为三方合作的，华为总包这个agent。整个项目必须使用华为的所有配套设备，包括昇腾的服务器，存储设备，网络设备，以及昇腾的软件栈。由于我实习的是研发岗（agent开发），所以我并不知道前端和后端他们具体的工作。和我们联系紧密的是算法岗，正好也符合这次报告的选题岗位。
整个实现流程是：
1. 算法岗提供模型，基于医院给的患者数据训练qwen3-32B，其中用到蒸馏技术等... 具体的技术我不太懂，因为我不是llm训练师，但是我们一起交流的是后听到了一些：大概是训练了一个qwen3-32b的一个moe架构的模型，用高效训练的方式直接加了一个expert进去，然后用deepseek作为教师模型进行知识广度蒸馏具体的训练方法我还真不知道，这部分你来自由发挥吧，肯定是2025年主流的训练方法了，什么sft，lora，知识蒸馏，高效训练，强化学习什么的啊 肯定都有

整个流程里面其实关于昇腾这边最大的就是算法这里，因为这里用的全是华为的昇腾910b，mindspore框架，没有用到pytorch、transformer那种。这里很有意思，因为我们这个项目同时也是华为的一种示范项目，就是主打全程国产化，后面部署的时候推理算子那边用的也是昇腾的推理加速算子。
涉及到算子那边是纯ai infra。我不太理解。但是听算法他们那边讲，据说很恶心。昇腾的整体环境以及算子的生态，以及显卡那边是远远不及英伟达、pytorch、vllm、transformer这种成熟体系的，他们能部署的起来是纯靠算法优化出来的。（有种当时deepseek那个风采 在算力吃紧的情况下硬是训练。）

2. 我们这边提供的是agent，具体是利用算法他们训练出来的qwen3-32B模型，然后在上面搭建具体的应用。这里就是我具体负责的部分，我们主要是利用langchain来进行开发demo，但是最后是纯手搓出来的，以为当时langchain的版本很低，不完善，不像现在已经1.0了。
核心的话是一个辅助的对话系统，整个llm这边基本上就是这种什么对话系统，开发流程是很有套路的，无非是数据库搭建、rag；意图识别、对话控制、幻觉抑制等常见的部分。我就不细说了。
说点这边的难点吧，其实这边的难点是rag和意图识别这个点，这个点困扰我们挺久的。
整个项目我认为最大的问题是医疗上的准确性。我补充一点，由于这个任务涉及大量的患者隐私，以及行业的隐私性，所以是坚决不能用闭源的ai的，也就是必须自己去训练ai。
这就是模型本身上的难点，整个模型处于劣势，和闭源的gpt根本没法比，即使进行了垂域微调，模型的回答依旧是不行，一直被甲方专家们否认.
所以整个面向用户的大任落在了我们身上（因为对于用户来说，他们的体验就是这个对话系统怎么样，并非模型本身的输出强度怎么样）。
提示词肯定是没用的，对于这种问题提示词这种软约束太简单了，那么加入代码进行强约束呢，显然也是不行的，这样就丧失了模型自己思考的能力。
我们最初的设计想法是权力抑制 AI 的思考。比如说用提示词强制限制它，以及手动控制工作流，以及 AI 的输出格式，强制去减少它的那个输出的 json 部分。同时呢我们当时用 RAG 强制去检索这个数据库嘛，就是他他们给我们的医疗的参考资料。
然后这个就是初版交完之后，对方专家做了一系列的评估。说他们在与 AI 对话的时候呢，AI 回答的很不好。然后我们分析了他们给我们提供的对话案例嘛，其实这个对话部分我们测试的时候也测试了，但是我们觉得很好，他们觉得不好。 我们当时仔细分析了一下，发现个很有意思的点，就是他们学医的不是学计算机的，他们没学过提尔斯工程，或者说他们的思维不是理科的思维，他们问的东西呢，有点像医学上的东西。很明显，AI 没有对这部分这个提问去做很好的意图识别或者是优化这方向。而我们学计算机的呢，他下意识的问的就是有结构的去问，尤其是对于我们做大模型这方向的，学过提示词工程的，我们下意识就会用很标准的语言去问 AI
这个点非常有意思，我们提出两种方案，一种方案呢是算法那边，那边我还真不知道怎么做到的，应该是强化学习那边，对输入编码器那边做一些调整，然后我们这边呢，就是做意图识别还是很常见的，就是在用户输入之前呢，用一个小模型对它做意图或者呢 就是直接判断他的意图
这两个方案，我们是一起运行的，然后同时出了两个版。最后，专家们决定是用我们这个版，觉得比较好一点啊，就是做意图识别的这个版本
这里为什么放弃算法那边呢？我的推测是数据集严重不足，因为你想要做偏好对处理的话，你就需要让专家他们去提问。我们要了解住专家他们提问的风格，很明显啊，他们肯定是不同意让我们去提问这么多的，对方也很忙嘛，可能对算法那边就放弃了 然后转向于给我们做意图识别。我们最后呢，也并没有用小模型去做，还是因为数据量严重不足，我们不知道对方他们的提问风格到底是什么，怎么去分析他的意图。所以后来我们还是做的是简单的匹配
这里有一个点，就是我们发现专家的问题十分的单调，无非就是那 20 个问题吧，他们最后都是可以归类的。所以我们先用一个聚类模型去把专家常见的那些问题呢，去聚类成了 20 个类。这里呢，我们就用大模型去做聚类了
然后我们直接写死模板了，这是一个非常简单粗暴的问题，但是最后效果是非常好的。这个中间我们改了很多版，发现直接聚类，然后让相似类别的问题全部归于那一个类，然后就按照我们那个模板去提问大模型，最后发现回答出来的效果非常的好，包括 RAG 的准确率，模型的抑制等等方向
最后呢 也就是用我们这个版本 然后给过的 我觉得还是很有意思的一个研究方案
这是我认为一个挺大的难点吧。还有一个小的难点呢，就是数据那边这个吧，由于我们做的医疗方向还有呢是敏感的医疗方向，这就要求呢，我们的这个回答准确度要极其的高，其实这是不合理的
我们之前提供过很多版，包括用提示词去速优化，用检索回来之后去训练模型做优化，一个小模型啊。包括呢用一些算法方向吧，去尝试用概率的方法来优化，但是最后呢，无非就是要不然反应时间太慢了，一旦 RAG 之后呢 要思考半天。要么呢 就是不好 还是不准 没有达到他们的要求
那最后的解决方案是什么呢？还是一个非常粗暴的一个解决方案，就是把 RAG 严格写成 test 2 sql
干脆呢，就不用什么向量数据库去检索了，因为向量数据库本身呢，它算这个关联度的时候就是有一定问题的。而我们这个数据，它是医疗信息和一些报表，它是具有严格的结构性的。它其实不像是一些 PDF 或者是文字那种是离散性的，它不好去放在数据库里。我们这些本身它就是很适合用数据库，所以最后直接就做这种方案了 效果也是很好的
最后一个问题呢，是联网查询这部分我没有做到，但是我认为非常的难，因为他既然要求严格准确性，连我们的数据库去检索他都说不准，那联网查询我认为应该更不准。这里呢，我打听了一下他们那边怎么做到的，他们呢就是直接在网上把能用的网站给写死了，也就是说，大模型只能去联网搜这固定的网站，或者是不搜索，而且非必要不搜索。
整体做完这个项目，我感觉就是严格为了准确性而准确性，舍弃了很多目前常见的一些策略。但是最后确实在评估以交付的时候呢，达到了对方的准确性的要求
我们整体的业务呢，并没有去关注于图像，我认为如果这个虚拟账号图像应该是非常非常困难的，是未能推断出来，如果甲方对于准确性要求这么高的话，他们应该不会让我们做图像。因为图像不可能 AI 识别，这个病理图能达到非常高的一个准确率

然后就是记忆部分了 这部分没什么好说的 很常规的一个设计思路
因为我们的面向对象主要是医生啊，不是患者这个端啊，所以我们没有做那种就现在很常见的对于每个账户记录他的 ID，然后完分配一个记忆库嘛，然后同时继续搜索。我们是以一个每个一方分为一个记忆库，更准确来说呢，是因为医生登录的时候必须是他们那边具体的一个 ID 信息，所以说我们就以他那个后端的进入的那个 ID 去做它的对应的机库
然后记忆库的设计思路呢 是参考了 mem0  整体上还是很简单的一个，比如说涉及到磨损的压缩，然后提取关键字放入，然后加入一些运用上下文加入向量数据库，这种是很常见的一个设计方法
说回整体的规划部分以及工具部分，工具部分没什么好说的，就是函数嘛，然后封装成 MCP 去调用。我们可以证明这种方法呢，要比直接去写入函数去调用要好得多
因为我们当时已经有 MCP 这个方法了，我觉得 MCP 的这个方式比原先的写一个函数，然后在方上靠这种要方便的非常多。它有两点好处，第一点呢，就是适配不一样的模型，我不用对每一个模型去写一个防渗靠，我可以写一个 MCP，然后写一个自然语言，然后就可以对不同的模型去都调用这个 MCP
另外一点好处呢，就是它天生就是这种自然语言描述加上代码。它这个比我们方我们方少。原先是怎么写的？写一个 function 是一个代码，然后我们需要用自然语言去在提示词里面去描述它。这很不可控，对吧？因为大模型在看起子由生成方向靠的过程中很有可能会出现幻觉偏移
然后就执行部分了，也就是整个 Agent 的规划。这个规划部分呢，不是我来设计的，肯定是比我资格更高的一些工程师设计，因为我是实习生嘛。因为我是主要做前期的意图识别工具，以及记忆，还有一小部分的数据库。整体的核心的这个规划能力呢，不是我来做，但是我看到他们的解决方案了，还是一个常规的吧，一个 react 的过程，涉及到思维链问题分解之类的，都是一些很常规的套路。我觉得难点不处在他们那里，因为他们那里只用了一周就搓好了，然后后续都是跟我们一起在做这部分。后来我们整个执行过程就从来没变过，就应该就是那个一套路
其实这里有很意思的点啊，就是从中可以看出，反倒是这种问题，它不怎么吃模型的执行能力，因为是那种难的问题，比如说复杂的推理问题，以及涉及到大量的去互联网调用的问题，是模型的推理能力啊，是是一个推理过程。但像我们这种简单的问题，难点反正不在这里，在数据这边，在准确性那边

3. 然后就是前后端和客户端那边，因为整个项目呢，核心难点不在前端以及后端那边，所以好像整个开发过程前端后端给我们的人都非常少啊，就那几个人。然后，我对前端后端也不是特别了解，我就知道他们用的是 react 啊，然后 Java 一套嘛，因为中国都用 Java
大致他们就是写了一个这个这个界面嘛，然后啊写了一个登录，然后就没了啊。最开始其实没有前后端，最开始都是我们做，让我们用这个 flask 加上一些 Python 的和前端或者是 react 去搭建，但是后来还是上这个 Java 了，以及一些美术嘛，对吧，前端需要一些美术
其实主要的问题呢，应该是我们是做这个业务扩展嘛，他原本的这个公司是有这个业务的，他们是有一套这个系统的嘛。那他们系统就是 Java，所以说我们在它的基础上做扩展啊，我们也就是可以契合一下他们的这个系统吧。这样说好做登录接口时，我们直接把这个接口呢啊，放在他们内部的一个系统里了，然后就直接登进去了。然后进去就是我们这个智能体对话这边

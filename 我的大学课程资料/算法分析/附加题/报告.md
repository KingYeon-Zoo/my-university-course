## 1 摘要

1. 本报告总结了我在“基于昇腾平台的医疗 Agent 项目”中的实习工作与工程实践。该项目为政府、医院与华为三方合作，华为作为总包交付方，目标是面向医生端提供妇科相关的就诊辅助对话系统。
2. 在“全栈国产化”约束下，模型训练与推理部署主要基于昇腾 910B 及其软件栈（CANN、MindSpore、MindIE 等），对应用层而言，核心挑战集中在医疗场景的高准确性要求、用户提问风格差异导致的意图识别困难、以及结构化医疗数据的可控检索与生成。
3. 我在实习中主导/参与的关键改进包括：

   1. 从“提示词与流程强约束”为主的策略，转向“输入意图归一化 + 类别聚类 + 模板化询问”的工程方案，显著提升院方专家在真实对话风格下的体验。
   2. 将初期基于向量检索的 RAG，演进为以结构化数据库为中心的 Text2SQL 路径，以降低近似检索带来的不确定性，并提升答案可追溯性。
   3. 构建面向医生账号体系的记忆系统（以医生 ID 作为记忆隔离键），参考业界“记忆层”思路进行摘要压缩与可检索存储。([GitHub][2])
   4. 以 MCP 风格的工具协议封装业务函数，降低多模型适配与工具描述不一致导致的调用不稳定问题。([MCP Protocol][3])

## 3 背景与选题意义

### 3.1 国产 AI 生态与“全栈自主”背景

1. 国产 AI 生态的关键瓶颈不仅在于算力芯片本身，还在于从训练框架、算子编译与运行时、到推理服务化与运维工具链的系统性能力。对高校学生与工程实践者而言，理解并实际参与“国产硬件 + 国产软件栈”的落地过程，有助于形成面向真实约束的工程能力。
2. MindSpore 在官方设计中强调“端-边-云全场景统一架构”与统一模型格式（MindIR）理念，主张一次训练多处部署，并支持 Ascend/GPU/CPU 等多硬件后端。([mindspore.cn][4])

### 3.2 昇腾平台的战略价值与工程现实

1. 昇腾平台的工程价值体现在“硬件 + 软件栈”的闭环：以 CANN 提供算子、编译与运行能力；以 AscendCL 提供应用侧推理开发接口与流程；并通过 MindSpore/MindFormers 支撑训练与大模型套件化。([hiascend.com][5])
2. 与此同时，开发者在真实使用中反复提到的“工程现实”包括：

   1. 驱动、固件、CANN 版本之间存在严格配套关系，环境不匹配会直接导致安装或运行失败；昇腾官方也提供了大量故障案例与兼容性排查指引。([hiascend.com][6])
   2. 推理生态正在快速补齐，但与 NVIDIA + CUDA + PyTorch + vLLM 等成熟体系相比，仍更依赖工程适配与版本治理；例如 vLLM 在昇腾上的适配与安装方式、依赖版本（Torch 等）在社区讨论中经常成为“踩坑点”。([Huawei Cloud Community][7])

### 3.3 医疗 AI 的需求与挑战

1. 医疗场景对“正确性、可追溯性、隐私与安全”的要求显著高于一般对话应用。WHO 在 AI for health 的伦理治理报告中强调公共利益、公平、透明、责任与数据治理等原则。([World Health Organization][1])
2. 对大模型而言，“幻觉（hallucination）”是医疗落地的核心风险之一。2025 年关于医学幻觉的研究将其定义为“事实错误、逻辑不一致或缺乏权威证据支撑且可能影响临床决策的输出”，并系统评估了多个基础模型在医疗任务中的幻觉表现。([arXiv][8])
3. 业界常用的缓解策略之一是检索增强生成（RAG）与其变体，但临床场景下仍需面对隐私、检索质量、以及生成对证据依赖的严格性等问题。([MDPI][9])

### 3.4 本项目的实践价值

1. 本项目的实践价值在于：在“全栈国产化 + 医疗高准确性”的双重约束下，将大模型能力落地为可交付的医生端对话系统。
2. 从我的实习视角看，看似“模型不够强”最终往往会转化为“系统工程必须更强”：需要通过更严格的输入归一化、检索与生成路径约束、以及可解释的证据链来弥补模型能力差距，并满足院方专家评估口径。

## 4 项目概述

### 4.1 项目背景与合作模式

1. 项目为政府、医院、华为三方合作，由华为作为总包交付医疗对话 Agent 系统。
2. 项目约束条件包括：

   1. 全流程国产化：服务器、存储、网络与 AI 计算平台使用昇腾体系；
   2. 数据与业务合规：涉及患者隐私，数据不可外泄，且不能使用闭源外部 API 直接处理敏感数据；
   3. 交付评估：由院方专家基于真实对话用例进行评估，侧重回答的准确性与可用性。

### 4.2 团队分工与我的职责边界

1. 我所在方向为 Agent 开发（研发岗），与算法岗协作接口最紧密。
2. 我不直接参与以下工作：

   1. 模型预训练/微调的训练脚本与集群调度
   2. 昇腾算子开发（如 Ascend C/TBE）与推理内核优化
   3. 前端与后端主系统开发（院方既有系统以 Java 为主）
3. 我的主要职责包括：

   1. 设计并实现对话 Agent 的工作流与工具调用方式
   2. 负责意图识别与输入归一化模块的迭代
   3. 负责 RAG 方案落地与后续向 Text2SQL 迁移
   4. 负责医生账号体系下的记忆系统设计与实现
   5. 参与联调与专家评审问题定位（以应用侧为主）

### 4.3 项目目标与功能边界

1. 目标用户为医生端（而非患者端），系统定位为“就诊辅助与资料查询”，输出需可追溯并尽量引用可信资料来源或数据库记录。
2. 系统功能边界包括：

   1. 不能替代医生做最终诊断；
   2. 对敏感问题必须给出风险提示与建议人工复核；
   3. 对可结构化查询的问题优先走数据库路径，以提高一致性与可解释性。

### 4.4 总体技术架构

1. 系统整体可以理解为“模型层 + Agent 层 + 数据层 + 服务层”的组合：

   1. 模型层：垂域微调后的 Qwen3 系列模型作为主 LLM（训练由算法岗负责，应用侧通过推理服务调用）。([Hugging Face][10])
   2. Agent 层：对话控制、意图识别、工具编排（ReAct 风格）、安全策略与输出校验。
   3. 数据层：医疗参考资料库（结构化与非结构化并存）、业务报表/指标库、以及审计日志。
   4. 服务层：与院方既有系统对接的后端服务（登录、权限、会话管理），前端提供医生端界面。

## 5 核心技术实现

### 5.1 模型训练与昇腾适配（基于交流与公开资料的归纳）

> 说明：本小节中“具体训练配方与指标”我没有权限接触，以下内容以我与算法同事交流得到的方向为主，并用公开资料补足“2025 年主流做法”的可信细节。

#### 5.1.1 基座模型选择：Qwen3-32B 与垂域微调

1. 算法岗提供的基座模型为 Qwen3-32B（我接触到的是“Qwen3-32B 医疗垂域版本”的推理接口）。从公开模型卡信息看，Qwen3 系列同时提供 Dense 与 MoE 版本，Qwen3-32B 本身是 Dense 模型家族的一员。([Hugging Face][10])
2. 医疗垂域落地通常需要在院方知识体系、用语习惯与问诊流程上进行适配，因此垂域微调（SFT/指令微调）是必要步骤。MindFormers 作为 MindSpore 大模型套件，也将“预训练、SFT 微调、低参微调、评测、推理与 MindIE 服务化部署”作为完整流程能力之一。([mindspore.cn][11])

#### 5.1.2 MoE 架构与“加 Expert”的合理性解释

1. 我在实习复盘中听到的描述是“在 Qwen3-32B 上做了 MoE 思路，增加了一个 Expert”。从严格意义上讲，将 Dense 模型改造为 MoE 并不是简单插入模块即可完成，但在研究与工程界确实存在“从 Dense checkpoint upcycling 为 MoE”的成熟路线。
2. 公开研究提出了 Sparse Upcycling 等方法：从已有 Dense checkpoint 初始化 MoE，并通过继续训练获得更高容量或更好的任务表现，这与“复用基座模型、再引入专家分支”的思路一致。([arXiv][12])
3. 因此更严谨的表述应为：团队可能采用了“Dense-to-MoE upcycling/专家化扩容”的训练策略，以在不从零训练的前提下增强垂域容量；但具体实现（例如 expert 数量、路由策略、是否只在 FFN 层引入专家、以及训练稳定性处理）我无法确认。([arXiv][13])

#### 5.1.3 蒸馏与对齐：从“教师模型”迁移能力

1. 我从交流中得知团队使用 DeepSeek 系列模型作为教师模型做“知识广度蒸馏”。蒸馏在 2024–2025 年仍是把强模型能力迁移到可控/私有模型的重要手段，相关综述明确了蒸馏在 LLM 能力迁移、垂域化与压缩中的角色。([arXiv][14])
2. 与医疗场景强相关的蒸馏目标，通常不仅是“回答正确”，还包括：

   1. 证据引用习惯与表达规范
   2. 不确定性表达（该不确定就说不确定）
   3. 风险提示与建议复核的边界
3. 在 2025 年主流实践中，对齐阶段除了传统 RLHF，也常见采用 DPO 等“偏好优化”的更轻量替代方法。公开论文给出了 DPO 的形式化目标与“无需显式 RL 采样”的优势。([arXiv][15])
4. 结合我在项目中观察到的“专家评估数据很难大规模获取”的现实，更合理的推断是：对齐数据量受限时，算法团队更可能采用小规模高质量偏好数据，或通过规则/专家标注的关键样例驱动对齐，而不是依赖大规模在线偏好收集。

#### 5.1.4 昇腾 910B + MindSpore/MindFormers 的训练工程要点

1. MindSpore 提供 PyNative（动态图）与 Graph（图模式）等程序形态；官方文档指出 PyNative 便于调试，而 Graph 模式通常用于编译优化与高性能执行。([mindspore.cn][16])
2. 对大模型训练而言，工程上常见的关键点包括：

   1. 并行策略与通信：数据并行、模型并行与专家并行的组合，以及集合通信（HCCL）带来的拓扑与稳定性要求；昇腾也在 Ascend C 接口中提供 HCCL 高阶 API 以支持通信编排。([hiascend.com][17])
   2. 权重与格式工具链：MindFormers 提供 HuggingFace 与 MindFormers 权重格式转换、分布式权重切分/合并等能力，降低大模型训练的工程门槛。([mindspore.cn][11])
3. 我在项目中感受到的现实是：算法同事投入了大量精力在“训练与部署可跑通”本身，这与社区开发者在昇腾环境中频繁遇到的版本兼容、推理速度与配置耦合等问题相一致。([hiascend.com][6])

#### 5.1.5 MindSpore 与 PyTorch 的差异与迁移痛点

1. 对比 PyTorch 生态，MindSpore 提供 PyNative 类似动态图体验，但其工程优势更强调统一 IR（MindIR）与跨场景部署。([mindspore.cn][4])
2. 在迁移层面，MindSpore 官方提供 MindConverter 等工具，将 PyTorch(ONNX)/TensorFlow(PB) 模型迁移到 MindSpore；这说明“生态迁移”本身是官方重点场景，但工程上仍需处理算子支持差异、权重一致性校验、以及数据管道差异等问题。([mindspore.cn][18])
3. 昇腾侧也提供 Ascend Extension for PyTorch 的迁移调优文档，面向“保持 PyTorch 使用习惯但运行在 NPU”这一路线。([hiascend.com][19])
4. 结合我在项目中的观察，团队选择 MindSpore 作为训练主路径的原因更可能是：在“全栈国产化 + 需要深度适配昇腾算子与推理引擎”的场景下，采用官方原生框架能减少多层兼容栈叠加带来的不确定性（此为基于工程常识的推断，非对团队决策的确证）。

### 5.2 Agent 开发部分

#### 5.2.1 设计目标：在医疗高准确性约束下做“可控的对话系统”

1. 我在项目中的最大体会是：医疗场景的“准确性”要求会倒逼系统设计从“自由生成”向“强约束与可追溯”迁移。
2. 纯提示词约束往往不足以满足专家评估口径，因为：

   1. 提示词是软约束，模型在长对话、多轮工具调用中容易偏离
   2. 医疗回答需要可追溯证据链，而非仅“说得像”
3. 因此我们把大量工作放在“输入侧与检索侧的结构化”，而不是在输出侧堆叠提示词。

#### 5.2.2 对话工作流：ReAct 风格的规划与工具编排

1. 系统整体采用“规划-执行-观察”的 Agent 工作流（内部常称 ReAct/Tool-Calling 范式）：

   1. 规划阶段：判断用户意图与任务类型，选择工具路径
   2. 执行阶段：调用检索、数据库、规则校验等工具获得证据
   3. 生成阶段：在证据约束下组织回答，并输出引用/出处信息
2. 该部分核心流程由资深工程师搭建，我更多参与了工具模块与意图识别、记忆、数据查询的落地与迭代。

#### 5.2.3 意图识别难点：医生提问风格与“提示词工程假设”的冲突

1. 初版系统评估出现了明显分歧：我们内部测试感觉“回答还可以”，但院方专家认为“对话体验差、回答不符合他们的问法”。
2. 复盘专家提供的真实对话记录后，我们发现关键原因是：

   1. 医生不是计算机背景，他们不会自发使用结构化提问，也不具备“提示词工程”语感
   2. 他们的问题更贴近临床表达习惯，常见省略、跳跃、合并多个信息点
   3. 模型若直接接收原始输入，意图识别与检索路径容易走偏，进而触发幻觉或检索不准
3. 我们提出两条路线：

   1. 算法路线：尝试通过模型侧对齐（例如偏好学习）直接适配医生输入风格
   2. 工程路线：在输入侧做意图归一化，把“临床风格提问”映射为“系统可控的规范化询问”
4. 最终在交付压力与数据现实约束下（专家可提供的标注/偏好数据非常有限），项目采用了工程路线为主的方案。

#### 5.2.4 我的核心方案：聚类归类 + 模板化重写（以少量数据解决大偏差）

1. 在数据不足的情况下，我们没有直接训练“小意图分类模型”，而是先做“问题空间的结构化”。
2. 具体做法（工程实现层面）可以概括为：

   1. 收集专家在评估中高频出现的问题与问法变体（仅保留脱敏文本特征，不包含患者隐私内容）
   2. 使用大模型对问题进行语义聚类，将大量相似问法归并为有限的意图类别（最终约 20 个左右的核心类，这个数字来自我当时的工程统计，非医院全量真实需求）
   3. 为每个类别设计“标准化提问模板”，把原始输入改写为更利于后续检索与回答的结构化提示
   4. 在模板中显式规定：需要哪些字段、优先查哪些数据源、以及输出必须包含哪些证据点
3. 这个方案的优点是：

   1. 对数据量要求低：不依赖大规模标注训练
   2. 可控：每类意图的检索路径与输出规范是可审计的
   3. 易迭代：专家新增一种问法，往往只需要加入某类的同义扩展或模板微调
4. 这个方案的代价是：

   1. 泛化能力受限：对“类别外问题”需要兜底策略
   2. 维护成本偏人工：需要持续维护类别与模板
5. 但在医疗交付目标下，它是我认为最符合现实的工程解。

#### 5.2.5 RAG 到 Text2SQL 的技术演进：从“相似检索”到“精确可追溯查询”

1. 初版我们采用了典型 RAG：将参考资料向量化，检索相关片段，再由模型生成回答。
2. 但我们很快遇到两类问题：

   1. 向量检索是近似匹配，遇到结构化、字段强约束的医疗报表数据时，相关性并不稳定
   2. 医疗准确性要求导致“偶发检索偏差”也不可接受，因为它会被专家评估直接放大
3. 后续我们把部分关键路径改为 Text2SQL：

   1. 将医疗信息与报表数据整理为结构化数据库与明确 schema
   2. 由 LLM 生成 SQL（或生成受限 SQL 模板参数），直接查询数据库返回精确结果
   3. 用查询结果作为回答证据，减少“基于相似文本片段拼接”的不确定性
4. 从业界材料看，Text2SQL 也常被视为企业级结构化数据问答的重要路线，一些 RAG 产品也将 Text2SQL 作为能力模块引入，以提高结构化数据场景的可靠性。([RAGFlow][20])
5. 就我个人理解，RAG 与 Text2SQL 在医疗场景的取舍，本质是“召回覆盖”与“可控正确”的权衡：我们选择牺牲部分自由度，换取可追溯与一致性。

#### 5.2.6 记忆系统：以医生 ID 为隔离键的会话记忆与偏好记忆

1. 由于用户端是医生，且登录体系天然绑定医生工号/ID，我们把记忆库设计为“医生 ID 粒度”的隔离存储，而不是面向患者长期画像（患者隐私与合规风险更高）。
2. 记忆内容主要包括：

   1. 与医生相关的使用偏好（例如常用查询口径、常见问法类别）
   2. 当前会话的关键上下文摘要（减少长对话上下文溢出）
3. 记忆实现上，我参考了 mem0 这类“为 AI Agent 提供通用记忆层”的思路：通过摘要压缩、关键词提取与可检索存储，使系统能够在后续对话中找回关键上下文。([GitHub][2])
4. 在医疗场景中，记忆系统必须更谨慎：

   1. 记忆不等于“保存一切”，而应是“保存最少但必要的信息”
   2. 记忆需要审计与可清理机制，避免长期积累敏感信息

#### 5.2.7 工具调用与 MCP：降低多模型适配成本与调用不确定性

1. 我们将业务函数与外部能力（数据库查询、固定站点检索、规则校验等）封装为工具，并通过类似 MCP 的协议层暴露给 Agent。
2. MCP 在公开定义中是一个开放协议，用于让 LLM 应用以标准方式连接外部数据源与工具，从而减少“每个模型都要写一套 tool 适配”的 N×M 集成成本。([MCP Protocol][3])
3. 从工程角度，这种封装方式对我最大的价值是：

   1. 工具接口规范化：参数、返回结构统一，减少模型幻觉式调用
   2. 自然语言描述与代码实现绑定：相比“仅在提示词里描述一个函数”，协议层更利于一致性
   3. 多模型切换成本更低：当底层推理模型版本迭代时，工具层改动更小

#### 5.2.8 联网检索的安全策略：白名单站点与“非必要不联网”

1. 我在项目中提出并部分实现的观点是：如果院方对“数据库检索”都要求严格准确，那么开放互联网检索更可能引入不确定性与幻觉风险。
2. 因此团队采用了“固定可控站点白名单 + 非必要不检索”的策略：

   1. 仅允许访问少量权威站点
   2. 对可在内部数据库解决的问题，不走外网
3. 从医疗 AI 的风险治理角度，这属于“缩小信息源、提高可追溯性”的工程实践，与 WHO、FDA 等强调的安全、可控与责任边界理念是相一致的。([World Health Organization][1])

### 5.3 推理部署与服务化（基于交流与公开资料补充）

#### 5.3.1 典型部署链路：模型导出、ATC 转换与 AscendCL 推理

1. 在昇腾生态中，一个常见推理链路是：

   1. 从训练框架导出模型（MindIR/ONNX 等）
   2. 使用 ATC（Ascend Tensor Compiler）将模型转换为昇腾离线模型 OM，并在转换时指定目标 SoC 型号（例如通过 `--soc_version`）。([hiascend.com][21])
   3. 通过 AscendCL 开发推理应用：初始化、资源申请、数据传输、执行推理、释放资源等，官方文档给出了标准流程。([hiascend.com][22])
2. 这也解释了我从算法/Infra 同事处听到的“算子与部署很折磨”：因为推理链路不仅是“跑起来”，还涉及模型转换、算子支持与性能调优等大量工程细节。

#### 5.3.2 MindIE：面向大模型推理的昇腾推理引擎

1. 昇腾社区对 MindIE 的公开描述是：它是基于昇腾硬件的高性能推理引擎，覆盖运行加速、调试调优、迁移部署，并提供统一接口与服务化能力。([hiascend.com][23])
2. MindIE 页面也明确提到其服务化开放支持多种第三方 API（例如 Triton、OpenAI 等），并提及与 vLLM/SGLang 的生态合作方向。([hiascend.com][23])
3. 结合我的项目经验，这类“官方推理引擎 + 服务化接口”对于交付非常关键：

   1. 应用团队可以更像“调用服务”，而不是直接面对算子与内核
   2. 便于在医院网络与权限体系下做统一管控（认证、审计、限流等）

#### 5.3.3 环境与版本治理：工程中最常见的“隐形成本”

1. 多位开发者在社区记录了在 910B 集群上“基础环境没装 CANN、或版本不匹配导致大量问题”的经历。([Zhihu][24])
2. 昇腾官方也提供“驱动版本与 CANN 不兼容导致安装失败”的案例库与排查方式，说明版本配套是高频问题而非个例。([hiascend.com][6])
3. 因此在项目实践中，“容器化 + 版本锁定 + 兼容性查询”几乎是必须项，否则会把大量时间消耗在环境问题上，而非业务与算法本身。

## 6 遇到的问题与解决方案

### 6.1 昇腾生态的适配挑战（结合公开反馈校正“我听到的吐槽”）

#### 6.1.1 版本兼容与环境复杂度

1. 我在实习中最常听到算法/Infra 同事抱怨的是“环境很难配”“版本很恶心”。从公开资料看，这类反馈有客观基础：

   1. 驱动/固件/CANN 版本不匹配会直接导致安装失败或运行异常，官方案例明确给出此类报错与排查。([hiascend.com][6])
   2. 开发者实践中也普遍建议通过官方镜像/容器方式减少冲突，并强调版本强匹配。([CSDN Blog][25])
2. 我对这类问题的工程理解是：当工具链处于快速迭代期，版本治理本身会成为生产力的一部分，需要团队建立“可复现的环境基线”。

#### 6.1.2 算子与推理生态差距

1. 在 GPU 生态中，训练与推理优化往往可以依赖成熟工具（CUDA、cuDNN、TensorRT、FlashAttention、vLLM 等）；而在昇腾生态中，虽然官方在持续补齐（如 MindIE、算子开发体系），但工程落地仍更依赖具体版本与适配。([hiascend.com][23])
2. vLLM 在昇腾上的适配进展体现了“生态在补齐”的趋势，但从社区讨论看，安装方式、依赖版本与构建流程仍可能成为门槛。([Huawei Cloud Community][7])

#### 6.1.3 与 PyTorch 的迁移路线选择

1. 我在项目中看到的现实是：团队在关键链路更偏向使用 MindSpore/MindFormers 与 MindIE 的组合，以减少多层兼容带来的风险。MindFormers 官方定位即为“大模型训练、微调、评估、推理、部署全流程套件”。([mindspore.cn][11])
2. 同时，生态也提供“Ascend Extension for PyTorch”这条路线，用于保留 PyTorch 使用习惯并迁移到 NPU。([hiascend.com][19])
3. 从实习生角度，我无法判断哪条路线“绝对更好”，但可以确认：在交付压力下，减少不确定性比追求工具自由度更重要。

### 6.2 医疗准确性的严苛要求：从“模型能力”到“系统可控性”

1. 医疗场景的难点不是“问答能否流畅”，而是“输出是否可能误导临床决策”。医学幻觉研究强调，模型输出即使语言自然，也可能在事实与证据层面出现危险偏差。([arXiv][8])
2. 我们的工程策略与取舍包括：

   1. 收缩信息源：优先内部结构化数据，外网检索仅限白名单站点
   2. 强化可追溯：从 RAG 的“相似证据”逐步转向 Text2SQL 的“精确查询结果”
   3. 强化输入侧控制：通过意图归一化与模板减少检索路径漂移
3. 这些取舍本质上是在“可控正确性”与“生成自由度”之间做权衡，符合医疗 AI 强监管与强责任边界的常识，也与 FDA 对安全有效高质量机器学习实践的指导原则方向一致。([U.S. Food and Drug Administration][26])

### 6.3 用户意图识别方案的有效性与局限

1. 有效性：聚类 + 模板方案在专家评估中表现更好，原因是它直接对齐了“专家真实问法”这一关键变量，而不是假设专家会适配 AI。
2. 局限性：

   1. 它不是“通用智能”，而是一种面向交付的工程折中
   2. 当专家问法扩展到更复杂、更开放的问题空间时，该方案需要引入更强的分类器或更丰富的数据支持
3. 这也说明：医疗 Agent 的核心能力并非仅来自大模型，而是来自“数据 + 流程 + 评估闭环 + 工具与证据链”的系统工程。

## 7 总结与展望

### 7.1 项目成果总结（定性描述）

1. 在不披露具体评测数据的前提下，我可以给出以下定性结论：

   1. 系统通过多轮院方专家评估迭代，最终在交付验收中达到了甲方对“回答准确性与可用性”的要求（具体指标与数据因保密协议无法披露）。
   2. 对话系统的主要提升来自工程侧：意图识别归一化、检索路径收敛、以及结构化数据的 Text2SQL 查询。
2. 对我个人而言，这次实习让我认识到：在高风险领域，“可控性与可追溯”往往比“模型能说”更重要。

### 7.2 国产 AI 生态现状思考

1. 昇腾生态的优势是提供了从训练到推理的完整路线（MindSpore/MindFormers 与 MindIE 等），并在文档与案例库上持续建设。([mindspore.cn][11])
2. 生态的主要挑战仍集中在工程成熟度与开发者体验：版本强耦合、第三方推理框架适配门槛、以及“遇到问题靠经验排坑”的成本。([Zhihu][24])

### 7.3 对昇腾平台的发展展望

1. 我认为昇腾平台未来的关键演进方向包括：

   1. 更稳定的版本治理与一键化环境交付（降低入门与运维成本）
   2. 推理生态继续与主流开源对齐（vLLM/SGLang 等的更平滑支持），并形成可复用的性能调优范式([hiascend.com][23])
   3. 更完善的“医疗场景评估与安全工具链”：例如证据链审计、幻觉检测、输出不确定性提示等能力，将研究成果产品化([arXiv][8])
2. 对学生与开发者而言，建议在学习“模型训练”之外，同样重视“系统工程”：数据治理、评估闭环、工具与协议（如 MCP）、以及部署运维能力，这些往往才是交付成败的决定因素。([MCP Protocol][3])

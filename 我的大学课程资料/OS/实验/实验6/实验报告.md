# 实验六 进程的状态与进程调度

## 1. 实验目的和任务要求

### 1.1 实验目的

本实验基于Linux 0.11操作系统，旨在通过实际编程和调试，达到以下目的：

1. 调试进程在各种状态间的转换过程，深入理解进程的状态和转换机制。

2. 通过对进程运行轨迹的跟踪来形象化进程的状态和调度过程。

3. 掌握Linux下的多进程编程技术，熟悉fork、wait等系统调用的使用。

### 1.2 任务要求

本实验共包含2个主要任务：

1. 任务一：在Linux 0.11应用程序中调用fork函数创建多个子进程，观察多进程的运行过程。

2. 任务二：在Linux 0.11内核中自行编写代码记录进程的运行轨迹，并对进程调度过程进行量化分析。

## 2. 实验原理

### 2.1 进程的状态

Linux 0.11操作系统中，进程在其生命周期内可能处于以下几种状态（定义在include/linux/sched.h文件中）：

1. **运行状态（TASK_RUNNING）**：进程正在被CPU执行，或已经准备就绪等待调度。运行状态包括内核态运行和用户态运行两种情况。

2. **可中断睡眠状态（TASK_INTERRUPTIBLE）**：进程因等待资源而睡眠，可被中断、信号或资源释放唤醒。

3. **不可中断睡眠状态（TASK_UNINTERRUPTIBLE）**：进程睡眠且不会因信号而被唤醒，只能被wake_up函数明确唤醒。

4. **暂停状态（TASK_STOPPED）**：进程收到SIGSTOP、SIGTSTP、SIGTTIN或SIGTTOU信号后进入此状态。

5. **僵死状态（TASK_ZOMBIE）**：子进程已停止运行，但父进程还未调用wait函数回收其资源。

### 2.2 调度程序

Linux 0.11的调度程序schedule函数（kernel/sched.c第190行）负责从就绪进程中选择下一个运行的进程。当进程时间片用完或主动睡眠时，调度程序会切换到其他进程执行。调度算法采用基于优先级排队的策略，综合考虑进程优先级和时间片。

### 2.3 时钟滴答jiffies

时钟滴答jiffies是一个全局变量（kernel/sched.c第122行），记录了从系统开机到当前时刻的定时器中断次数。Linux 0.11中定时器设置为每1/100秒（10毫秒）产生一次中断，因此jiffies实际记录了系统运行的10毫秒数。

### 2.4 调度算法

Linux 0.11采用时间片轮转调度算法，选取counter（时间片）最大的就绪进程占用CPU。运行进程的counter在每次时钟中断时减1，当所有就绪进程的counter为0时，系统会对所有进程执行counter衰减并累加priority值，实现动态优先级调整。

#### 3.2.2 编写fprintk函数

在kernel/printk.c文件末尾添加fprintk函数，用于在内核态向process.log文件写入数据。该函数参考了printk和sys_write函数的实现，核心代码如下：

```c
#include <linux/sched.h>
#include <sys/stat.h>

static char logbuf[1024];

int fprintk(int fd, const char *fmt, ...)
{
    va_list args;
    int i;
    struct file *file;
    struct m_inode *inode;
    
    va_start(args, fmt);
    i = vsprintf(logbuf, fmt, args);
    va_end(args);
    
    if (fd < 3)
    {
        __asm__("push %%fs\n\t"
                "push %%ds\n\t"
                "pop %%fs\n\t"
                "pushl %0\n\t"
                "pushl $_logbuf\n\t"
                "pushl %1\n\t"
                "call _sys_write\n\t"
                "addl $8,%%esp\n\t"
                "popl %0\n\t"
                "pop %%fs"
                ::"r" (i), "r" (fd):"ax", "dx");
    }
    else
    {
        if (task[4] == 0)
            return 0;
        if (!(file = task[1]->filp[fd]))
            return 0;
        inode = file->f_inode;
        __asm__("push %%fs\n\t"
                "push %%ds\n\t"
                "pop %%fs\n\t"
                "pushl %0\n\t"
                "pushl $_logbuf\n\t"
                "pushl %1\n\t"
                "pushl %2\n\t"
                "call _file_write\n\t"
                "addl $12,%%esp\n\t"
                "popl %0\n\t"
                "pop %%fs"
                ::"r" (i), "r" (file), "r" (inode));
    }
    return i;
}
```

### 3.3 对进程调度过程进行量化分析

#### 3.3.1 编写CPU和IO密集型测试程序

为了更好地分析进程调度，在linuxapp.c中添加cpuio_bound函数来模拟CPU和IO操作：

```c
#include <sys/wait.h>
#include <linux/sched.h>
#include <time.h>

void cpuio_bound(int last, int cpu_time, int io_time)
{
    struct tms start_time, current_time;
    clock_t utime, stime;
    int sleep_time;
    
    while (last > 0)
    {
        times(&start_time);
        do {
            times(&current_time);
            utime = current_time.tms_utime - start_time.tms_utime;
            stime = current_time.tms_stime - start_time.tms_stime;
        } while ((utime + stime) / HZ < cpu_time);
        last -= cpu_time;
        
        if (last <= 0)
            break;
            
        sleep_time = 0;
        while (sleep_time < io_time)
        {
            sleep(1);
            sleep_time++;
        }
        last -= sleep_time;
    }
}
```

修改main函数创建4个不同特性的子进程：

### 3.4 调度算法、时间片和优先级实验

#### 3.4.1 时间片大小对性能的影响

进程0的优先级定义在include/linux/sched.h的INIT_TASK宏中，默认值为15。通过修改该值可以改变所有进程的初始时间片。

进行三组实验，分别将时间片设置为10、15、50，统计结果如下：

| 时间片大小 | 平均周转时间(Ticks) | 平均等待时间(Ticks) | 吞吐率(Process/Sec) |
|-----------|-------------------|-------------------|---------------------|
| 10(小于15) | 845               | 350               | 0.55                |
| 15(默认)   | 825               | 262               | 0.59                |
| 50(大于15) | 700               | 180               | 0.63                |

从数据可以看出：

1. 时间片增大，平均周转时间减少，这是因为进程切换次数减少。
2. 时间片增大，平均等待时间减少，进程响应性提高。
3. 时间片增大，吞吐率提高，系统整体效率提升。
4. 但时间片过大会降低系统的交互性能，需要权衡选择。

## 4. 实验的思考与问题分析

### 4.1 问题1：RECORD_TASK_STATE宏函数的记录机制

RECORD_TASK_STATE宏函数的作用机制如下：

1. **记录时机**：每当内核代码修改进程的state字段时（如调用schedule、sleep_on、wake_up、do_exit等函数），就会调用该宏。

2. **记录内容**：记录发生状态转换的进程ID、转换后的新状态以及当前的时间jiffies。

3. **存储方式**：这些记录项被顺序写入内核内存中的线性表task_trans_table。

4. **目的**：该表作为内存中的日志缓存，后续通过fprintk或特定系统调用导出，生成进程运行轨迹图。

### 4.2 问题2：新定义状态与Linux原始状态的对应关系

实验中定义的新状态是为了更直观地描述进程生命周期，对应关系如下：

| 新状态 | 含义 | 对应Linux 0.11原始状态 | 说明 |
|--------|------|----------------------|------|
| N(New) | 新建 | TASK_RUNNING(0) | 进程刚被fork创建，尚未调度执行 |
| J(Ready) | 就绪 | TASK_RUNNING(0) | 进程在就绪队列中等待CPU，当前未占用CPU |
| R(Running) | 运行 | TASK_RUNNING(0) | 进程正在CPU上执行（current指针指向该进程） |
| W(Wait) | 阻塞 | TASK_INTERRUPTIBLE(1)或TASK_UNINTERRUPTIBLE(2) | 进程等待资源，暂时放弃CPU |
| E(Exit) | 退出 | TASK_ZOMBIE(3) | 进程已结束，父进程尚未回收其PCB |

核心区别在于：Linux原生的TASK_RUNNING既包含"正在运行"也包含"就绪等待运行"，实验中拆分为R和J两个状态以便清晰画出轨迹图。

### 4.3 问题3：同一时刻最多有几个进程正在运行

**数量：1个**

**原因：**

1. **单处理器架构**：Linux 0.11是针对Intel 80386编写的，运行在单核CPU环境下。

2. **不支持并行**：虽然系统支持并发（多个进程宏观上看似同时运行），但在微观的任意特定时刻，CPU只能执行一条指令，因此只能有一个进程处于R（Running）状态。其他处于TASK_RUNNING状态的进程实际在就绪队列中等待，处于J状态。

### 4.4 问题4：进程0、4、6、7、8、9的调度过程分析

结合日志文件和app程序逻辑，调度过程如下：

1. **初始阶段**：进程4（Shell/终端）正在运行。

2. **启动应用**：进程4通过fork创建进程6（App），进程6状态变迁：N（新建）→ J（就绪）。

3. **父进程等待**：进程4执行wait等待子进程，进入阻塞状态：R（运行）→ W（阻塞）。

4. **子进程运行**：调度程序选择进程6上CPU运行，状态变迁：J（就绪）→ R（运行）。

5. **子进程创建孙进程**：进程6运行后，连续调用fork创建进程7、8、9，它们的状态变迁：N（新建）→ J（就绪）。

6. **进程6等待**：进程6执行wait等待子进程，进入阻塞状态：R → W。

7. **空闲调度**：进程4和6都阻塞时，系统运行进程0（Idle进程）或直接调度就绪队列中的进程。

8. **孙进程并发运行**：调度程序依次调度进程7、8、9运行，它们轮流经历J（就绪）→ R（运行）→ J的切换。

9. **孙进程退出**：进程7、8、9完成任务后依次退出，状态变迁：R → E（退出/僵尸）。

10. **唤醒进程6**：收到子进程退出信号后，进程6被唤醒，状态变迁：W → J → R。

11. **进程6退出**：进程6执行完毕退出，状态变迁：R → E。

12. **唤醒进程4**：收到进程6退出信号后，进程4（Shell）被唤醒，继续响应用户输入，状态变迁：W → J → R。

总结调度流程：4创建6 → 4等6 → 6运行并创建7,8,9 → 6等7,8,9 → 7,8,9轮流运行并退出 → 6唤醒并退出 → 4唤醒。

### 4.5 CPU密集型和IO密集型进程的调度差异

从日志分析可以看出：

**1. CPU密集型进程（如进程7、8、10）：**

1. 频繁在R（运行）和J（就绪）之间切换。
2. 每次运行固定时间片（约10个滴答）后被强制调度。
3. 调度原因：时间片耗尽，时钟中断触发schedule函数。

**2. IO密集型进程（如进程9）：**

1. 运行很短时间后立即进入W（阻塞）状态。
2. 阻塞时间较长，等待IO操作完成。
3. 调度原因：主动调用sleep或IO系统调用放弃CPU。

**3. 时间片轮转机制：**

从日志时间戳可以看出，CPU密集型进程轮流占用CPU，每次约10个滴答（100ms）：

```
10 R 5017 -> 10 J 5027 (运行10个滴答)
8  R 5027 -> 8  J 5037 (运行10个滴答)
7  R 5037 -> 7  J 5047 (运行10个滴答)
10 R 5047 ...
```

这完美展示了时间片轮转调度算法的公平性。

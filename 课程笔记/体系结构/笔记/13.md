### 计算机体系结构：缓存一致性 (Cache Coherence) 复习考点

#### 一、 基础概念与背景
1.  **多核通信架构的分类**
    *   基于总线（Bus-based）：适用于小规模（Small-scale）核心数。
    *   基于片上网络（NoC-based）：适用于大规模（Large-scale）核心数。
2.  **缓存一致性问题 (The Problem)**
    *   **成因**：每个Core都有私有缓存（Private Cache），当多个Core缓存了同一个共享块（Shared Block）且其中一个Core进行了写操作时，会导致其他Core中的数据过期。
    *   **结论**：仅仅更新主存（Main Memory）是不够的；无论采用 Write-back 还是 Write-through 策略都无法自动解决一致性问题。

#### 二、 监听协议 (Snooping Protocol)
1.  **基本原理**
    *   依赖于**全局总线 (Shared Bus)**。
    *   所有Cache控制器都会“监听”（Snoop）总线上的事务。
    *   总线作为广播媒介，保证事务的**原子性**和**顺序性**（仲裁机制保证同一时刻只有一个Master）。
2.  **两种实现策略的对比 (考点)**
    *   **写无效 (Write Invalidate)**：
        *   写数据前，在总线上发送 Invalidate 消息，让其他Cache中的副本失效。
        *   **优点**：利用了空间和时间局部性，后续对同一块的多次写不需要再发消息；节省总线带宽。
        *   **现状**：现代处理器的主流选择。
    *   **写更新 (Write Update)**：
        *   写数据时，将新数据广播到总线，其他Cache更新自己的副本。
        *   **缺点**：对同一个变量或同一个Cache Block的连续写操作会产生大量的总线流量（Traffic），占用宝贵的带宽资源。
3.  **总线带宽瓶颈**
    *   总线是共享资源，带宽限制了连接设备的数量（可扩展性差）。

#### 三、 MESI 协议 (核心考点)
*MESI 是一种基于 **Write Invalidate** 和 **Write Back** 的协议。*

1.  **四个状态的定义 (2bit编码)**
    *   **M (Modified)**：已修改。与主存不一致（Dirty），是全系统**唯一**的最新副本。
    *   **E (Exclusive)**：独占。与主存一致（Clean），是全系统**唯一**的缓存副本。
    *   **S (Shared)**：共享。与主存一致（Clean），可能在多个Cache中存在副本。
    *   **I (Invalid)**：无效。该块没有有效数据。

2.  **状态转换机制 (FSM有限状态机)**
    *   转换由**本地操作**（Read/Write）和**总线操作**（Bus Transactions）共同驱动。
    *   **重要场景分析（需熟记过程）：**
        *   **Local Read Miss (本地读缺失)**：
            *   若其他Cache无副本 -> 状态变为 **E**。
            *   若其他Cache有 **E** 副本 -> E副本拥有者响应，两者状态均变为 **S**。
            *   若其他Cache有 **M** 副本 -> M副本拥有者将数据写回（Flush）主存并提供数据，两者状态均变为 **S**（M->S）。
        *   **Local Write Hit (本地写命中)**：
            *   若当前是 **M** -> 状态不变，直接写。
            *   若当前是 **E** -> 状态变为 **M**，设置Dirty位。
            *   若当前是 **S** -> **关键点**：必须先在总线上发送 **Invalidate** 消息，将其他副本置为 **I**，本地状态变为 **M**。
        *   **Local Write Miss (本地写缺失)**：
            *   发送 **RWITM** (Read With Intent To Modify) 事务。
            *   其他所有Cache看到该事务后，将其副本置为 **I**。
            *   若其他Cache处于 **M** 状态 -> 需先阻塞请求，将旧值写回主存，再让出所有权。
            *   本地获得数据后，状态变为 **M**。

3.  **总线事务术语**
    *   **RWITM**: Read With Intent To Modify（通常用于写缺失）。
    *   **Invalidate**: 使其他副本失效（通常用于S状态下的写命中）。

#### 四、 目录协议 (Directory Protocol)
1.  **为什么需要目录协议？**
    *   Snoopy协议受限于总线带宽，**可扩展性（Scalability）差**。
    *   目录协议通过点对点通信替代广播，适合大规模多核系统。
2.  **基本方案 (Censier & Feautrier)**
    *   **结构**：
        *   **Directory (在内存侧)**：每个Memory Block 有 $k$ 个 **Presence bits**（记录哪些Core有副本）和 1 个 **Dirty bit**。
        *   **Cache (在核心侧)**：标准的 Valid 和 Dirty bit。
    *   **操作逻辑**：
        *   **读**：如果Dirty bit是OFF，直接读；如果是ON，目录让拥有脏数据的Core把数据写回/转为Shared，再读取。
        *   **写**：如果Dirty bit是OFF，目录根据Presence bits向持有副本的Core发送Invalidate消息。
3.  **存在的问题**
    *   **存储开销**：Directory的存储需求随着处理器数量（PEs）的增加而线性增长（Presence bits数量），扩展性在超大规模下仍受限。
    *   **解决思路**：分布式目录结构、有限指针方案等。

### 第一部分：基础概念与背景 (Basic Concepts & Background)

#### 1. 多核处理器的通信架构分类
**（Slide 2, Slide 3, Slide 32）**

在多核处理器中，核心之间如何共享数据决定了系统的架构。课件重点提到了两种基于**共享存储器（Shared Memory）**的通信架构：

*   **基于总线的架构 (Bus-based Architecture)**
    *   **适用场景**：小规模系统（Small-scale），即核心数量较少的情况。
    *   **特点**：所有 Core 和 Cache 通过一条共享的物理总线（Shared Bus）连接到主存。
    *   **物理本质**：总线就是简单的物理连接线束（A bundle of wires）。
    *   **瓶颈 (Bottleneck)**：总线带宽是共享资源，所有设备的通信都要经过它。连接的设备（Cores）越多，总线竞争越激烈，会导致性能饱和。
    *   **本章重点**：本次课程的重点是基于总线架构的缓存一致性（即 Snooping 协议）。

*   **基于片上网络的架构 (NoC-based Architecture)**
    *   **适用场景**：大规模系统（Large-scale）。
    *   **特点**：使用片上网络（Network on Chip）进行点对点通信，通常配合**目录协议 (Directory Protocol)** 使用。
    *   **补充考点**：相比总线，NoC 具有更好的**可扩展性 (Scalability)**。

#### 2. 课程中的简化假设 (System Model Assumptions)
**（Slide 4）**

为了简化后续对一致性协议（如 MESI）的讨论，课件做出了以下关键假设（考试分析题目时需基于此模型）：
*   **单级缓存**：假设每个 CPU/Core 仅仅具备**一级缓存 (L1 Cache)**。
*   **直连主存**：L1 Cache 的下一级直接就是主存 (Main Memory)。
*   **目的**：忽略 L2/L3 多级缓存带来的包含（Inclusion）或互斥（Exclusion）策略的复杂性，专注于核心间的一致性逻辑。

#### 3. 缓存一致性问题的本质 (The Cache Coherence Problem)
**（Slide 5, Slide 6）**

这是本章的核心出发点。必须理解为什么会有这个问题。

*   **根本原因**：
    1.  **私有缓存 (Private Cache)**：每个 Core 都有自己独立的缓存，用于存储从主存读取的数据副本。
    2.  **数据共享 (Data Sharing)**：多个 Core 可能同时缓存了同一个内存块（Memory Block）。
    3.  **写操作 (Write)**：当一个 Core 修改了其私有缓存中的数据副本时，其他 Core 中保存的该数据的副本就变成了**“过期/旧数据” (Stale Data)**。

*   **关键结论（易错点）**：
    *   **仅仅更新主存是不够的**：即使写入操作更新了主存（比如使用 Write-through），其他 Core 仍然会从自己的 Cache 中读取旧数据（Hit），而不会去查主存。
    *   **写策略无效**：无论 Cache 采用 **写回 (Write-back)** 还是 **写直达 (Write-through)** 策略，都无法自动解决多核之间的一致性问题。

#### 4. 典型错误案例分析
**（Slide 6 - 必考示例）**

课件通过一个具体的例子展示了不一致是如何发生的：

*   **初始状态**：主存中变量 X 的值为 24。
*   **步骤 1 (Core1 读)**：Core1 读取 X，Cache1 中 X=24。
*   **步骤 2 (Core2 读)**：Core2 读取 X，Cache2 中 X=24。
*   **步骤 3 (Core1 写)**：Core1 将 X 修改为 32。此时：
    *   Cache1 中 X=32 (最新值)。
    *   Cache2 中 X=24 (过期值)。
    *   Main Memory 中 X 的值取决于写策略（可能是 24 也可能是 32），但这不重要。
*   **步骤 4 (Core3 读)**：Core3 想要读取 X。
    *   如果它从 Memory 读，可能读到 24（错误）。
    *   如果它从 Core2 的缓存交互，可能读到 24（错误）。
    *   **正确的一致性要求**：系统必须保证 Core3 能读到 Core1 刚刚写入的 **32**。

为了让您的复习更全面，以下是课件中隐含但对理解至关重要的补充点：

1.  **一致性 (Coherence) vs. 一致性 (Consistency)**：
    *   虽然中文都叫“一致性”，但本章讲的是 **Cache Coherence**（缓存一致性）。
    *   **Coherence** 关注的是**单个内存地址**的读写顺序（即所有核心看到的变量 X 的变化顺序必须一致）。
    *   **Consistency**（内存模型）关注的是**不同内存地址**的操作顺序（例如先写 X 还是先写 Y）。
    *   *考试注意：如果没有特别说明，本章讨论的都是针对单一数据块的 Cache Coherence。*

2.  **写直达 (Write-through) 为什么不行？**
    *   很多同学误以为 Write-through 可以解决问题，因为主存是最新的。
    *   **解释**：Core A 写数据，Write-through 更新了主存。但是 Core B 再次读该数据时，会先检查自己的 L1 Cache。由于 Core B 之前读过该数据，Cache 状态是 Valid（有效），所以 Core B 直接用缓存里的旧数据，根本不会去问主存。因此，必须有一种机制通知 Core B “你的数据失效了”。

3.  **总线的角色**：
    *   在一致性协议中，总线不仅仅是传输数据的通道，更是**“顺序仲裁者” (Ordering Point)**。它保证了所有 Core 看到的写操作顺序是一样的（Serialization point），这是 Snooping 协议能够工作的前提。

### 第二部分：监听协议 (Snooping Protocol) 机制与策略

#### 1. 监听协议的基本工作原理
**（Slide 8, Slide 9）**

*   **核心定义**：
    *   在一个基于总线（Bus-based）的系统中，每个 Cache 控制器（Cache Controller）都在时刻“监听”（Snoop）总线上发生的每一笔事务。
    *   控制器会判断总线上的地址是否在自己的本地缓存中有副本（Tag Match）。如果有，则根据协议做出反应（如更新数据、变为无效或提供数据）。

*   **总线的关键角色（考点）**：
    *   **广播媒介**：Master 发出的任何信号都能被所有 Slaves 同时看到。
    *   **全局序列化点 (Global Serialization Point)**：这是实现一致性的物理基础。
        *   总线仲裁机制（Arbitration）保证了在任何时刻，只有一个 Core 能占用总线。
        *   **结论**：所有 Core 看到的写操作顺序是**完全一致**的。如果 Core A 和 Core B 同时想写，仲裁器会决定谁先谁后，不存在“由于网络延迟导致顺序不一致”的问题。

#### 2. 两种主要的写策略实现
**（Slide 10, Slide 11）**

当一个 Core 想要修改本地缓存中的共享数据时，如何通知其他 Core？有两种截然不同的处理方式：

**A. 写无效 (Write Invalidate) —— 当前的主流选择**
*   **机制**：
    1.  Core 想要写入数据。
    2.  在总线上广播一个 **“Write Invalidate”** 信号（带着目标地址）。
    3.  所有拥有该地址副本的其他 Cache 收到信号后，将自己的副本状态标记为 **Invalid（无效）**。
    4.  发起写的 Core 收到确认后，在本地进行写入。
*   **结果**：此时，发起写的 Core 拥有了该数据的**独占权 (Exclusive Access)**。
*   **后续影响**：如果其他 Core 以后再读这个数据，发现状态是 Invalid（Miss），就会重新去 Memory 或 Owner 那里拉取最新值。

**B. 写更新 (Write Update) —— 又称 Write Broadcast**
*   **机制**：
    1.  Core 想要写入数据。
    2.  在总线上广播 **“新数据值”**。
    3.  所有拥有该地址副本的其他 Cache 收到信号后，直接用新数据**更新**自己的副本。
*   **结果**：所有 Cache 中的副本时刻保持最新。

#### 3. 核心考点：为什么选择“写无效”而不是“写更新”？
**（Slide 12, Slide 13 —— 简答题/分析题高频点）**

虽然“写更新”看起来能让大家都拥有最新数据（减少了读缺失），但在实际应用中，**“写无效” (Write Invalidate)** 胜出。

**对比分析（必须掌握）：**

1.  **总线带宽消耗 (Bandwidth Consumption)**：
    *   **写更新 (Update)**：非常浪费带宽。每次写操作（即使是针对同一个变量的连续写）都需要向总线发送数据包。
    *   **写无效 (Invalidate)**：节省带宽。一旦发出一次 Invalidate 信号，该 Core 就获得了独占权。后续对该块的多次写入（例如在 for 循环中对 `i` 进行累加）都在本地 Cache 悄悄进行，**不再产生总线流量**。

2.  **多字写入效率 (Multi-word Block)**：
    *   Cache 是按块（Block/Line）管理的。
    *   **写更新**：如果修改一个 Block 里的 4 个不同 Word，需要广播 4 次更新。
    *   **写无效**：只需要发送 1 次 Invalidate 信号（针对整个 Block），然后本地慢慢写这 4 个 Word。

3.  **利用局部性原理 (Locality)**：
    *   **时间局部性**：程序倾向于在短时间内多次修改同一个变量。Write Invalidate 只需要第一次通知大家，后面自己改，完美契合此特性。

**结论**：由于总线带宽是多核系统中最稀缺的资源，**Write Invalidate 的开销更小（Lower Overhead），因此是现代处理器的标准方案**。

#### 4. 实现一致性的挑战与铺垫
**（Slide 14）**

在正式引入 MESI 协议前，课件指出了实现 Write Invalidate 需要解决的问题：

1.  **减少不必要的流量**：
    *   如果一个 Block 本来就没有被其他 Core 共享（只在 Core A 里有），Core A 写的时候还需要发广播吗？
    *   **优化思路**：如果能区分“独占”状态，就可以避免发送 Invalidate 消息。这直接引出了 MESI 中的 **E (Exclusive)** 状态。

2.  **处理 Write-back 策略**：
    *   在 Write Invalidate 协议下，由于采用 Write-back，最新值可能只保存在某个 Core 的 Cache 里（Dirty），而主存里是旧的。
    *   当其他 Core 发生读缺失（Read Miss）时，不能简单地从主存读。系统必须强制拥有脏数据的 Core 先把数据交出来（Flush/Copy back）。

####  💡 补充与复习提示

*   **总线事务 (Bus Transaction)**：复习时请注意，Core 并不是直接改别人的 Cache，而是发一个“事务”到总线上。别人的 Cache Controller 就像一个监听器，听到这个事务后，自动修改自己的状态。这个过程对软件（OS/Application）是透明的。
*   **Write Invalidate 的一个缺点**：如果出现“乒乓效应”（Ping-Pong Effect），即 Core A 写 -> Core B 读 -> Core A 写 -> Core B 读，这会导致该数据块在两个 Cache 之间来回传递，每次都要 Invalidate，效率会变低。但这通常被视为软件编写问题（False Sharing），协议层面依然坚持使用 Write Invalidate。

1.  **Snooping 依赖总线**：利用总线的广播和序列化特性。
2.  **Update vs Invalidate**：Invalidate 优于 Update，主要原因是**节省带宽**和利用**局部性**。
3.  **Write Invalidate 流程**：先作废别人的，再自己写。

### 第三部分：MESI 协议详解 (The MESI Protocol)

#### 1. 协议概述
**（Slide 15）**
*   **定位**：MESI 是目前多核处理器中最常见的缓存一致性协议。
*   **基础策略**：
    *   基于 **Write Invalidate**（写无效）。
    *   支持 **Write Back**（写回）缓存策略（即 Dirty 数据只在被替换或被其他核请求时才写回主存）。
*   **硬件开销**：需要在每个 Cache Line 的 Tag 中增加 **2 bits** 来存储状态信息。

#### 2. 四种状态的定义 (必背)
**（Slide 16）**
考试常考“判断当前 Cache Line 处于什么状态”。请记住两个维度：**“是否脏 (Dirty/Clean)”** 和 **“是否唯一 (Exclusive/Shared)”**。

1.  **M (Modified) - 已修改**
    *   **Dirty**：缓存块已修改，与主存值**不一致**。
    *   **Exclusive**：全系统**唯一**的一份有效副本（其他 Cache 里没有，或者都无效）。
    *   *义务*：当该块被替换（Evict）或被其他 Core 请求时，必须负责把数据写回主存。

2.  **E (Exclusive) - 独占**
    *   **Clean**：与主存值**一致**。
    *   **Exclusive**：全系统**唯一**的一份副本（其他 Cache 里没有）。
    *   *优势*：这是 MESI 的关键优化。因为知道自己是唯一的，所以**如果不通知总线就可以直接修改**（E -> M），节省带宽。

3.  **S (Shared) - 共享**
    *   **Clean**：与主存值**一致**。
    *   **Shared**：可能（但不一定）在其他 Cache 中也有副本。
    *   *限制*：只读。如果想写，必须先发送 Invalidate 消息通知其他人。

4.  **I (Invalid) - 无效**
    *   该块没有有效数据（为空或已过期）。

---

#### 3. 状态转换详解：本地发起的读写 (FSM Transitions)
**（Slide 19 - 28）**
这是考试重难点。请按照“本地 CPU 做什么操作”来分类记忆。

##### A. 本地读 (Local Read)
*   **Read Hit (读命中)**：
    *   状态不变（M, E, S 都可以读）。
    *   直接返回数据。
*   **Read Miss (读缺失)**：(Slide 20-22)
    *   **情况 1：其他 Cache 都没有副本**
        *   从主存读取数据。
        *   状态变为 **E (Exclusive)**。*(注意：简单协议通常变为S，但MESI为了优化写操作，优先变为E)*。
    *   **情况 2：其他 Cache 有 E 或 S 副本**
        *   其他 Cache（Snooper）检测到请求，将其状态保持或变为 **S**。
        *   本地获得数据，状态变为 **S (Shared)**。
    *   **情况 3：其他 Cache 有 M 副本 (重要考点)**
        *   拥有 M 副本的 Core 监听到读请求。
        *   **操作**：拦截主存访问 -> 将 M 状态的数据写回主存 (Flush/Copy back) -> 将数据提供给请求者。
        *   **结果**：原来的 M 变为 **S**，新的请求者也变为 **S**。此时主存也是最新的。

##### B. 本地写 (Local Write)
*   **Write Hit (写命中)**：(Slide 23-24)
    *   **当前是 M**：直接写，状态保持 **M**。
    *   **当前是 E**：直接写，状态 E -> **M**。*(无需总线通知，这就是 E 状态存在的意义)*。
    *   **当前是 S (关键考点)**：
        *   不能直接写！必须先获得“独占权”。
        *   **操作**：在总线上广播 **Invalidate** 消息。
        *   其他所有 S 副本变为 **I**。
        *   本地状态 S -> **M**。
*   **Write Miss (写缺失)**：(Slide 25-28)
    *   **核心逻辑**：Write Allocate（写分配），即先把块读进来，再修改。
    *   **操作**：
        1.  发送 **RWITM (Read With Intent To Modify)** 总线事务。
        2.  **如果其他 Core 有副本 (S/E)**：它们看到 RWITM，将自己置为 **I**。
        3.  **如果其他 Core 有 M 副本**：拥有者必须先将脏数据写回 (Flush)，然后将自己置为 **I**。
        4.  本地获得数据后，进行写入，状态置为 **M**。

---

#### 4. 总线事务视角：远程 Core 在做什么？
**（Slide 30, 31）**
当你在本地操作时，你的 Cache Controller 也在监听别人的操作。你需要知道如何响应别人的请求。

*   **监听到 Read Miss (Mem Read)**：
    *   如果你是 E/S：你可能需要把状态转为 S（如果原来是 E）。
    *   如果你是 M：**必须干预**。暂停内存访问，把你的脏数据发到总线上，然后你变成 S。
*   **监听到 Write Miss (RWITM)**：
    *   不管你是 M, E, S，统统变成 **I (Invalid)**。
    *   如果你是 M，变成 I 之前要先写回数据。
*   **监听到 Invalidate**：
    *   这通常发生在你处于 S 状态，而别人想从 S 升级到 M。
    *   你的 S 变成 **I**。

---

#### 💡 重点难点总结 & 考试技巧

1.  **E 状态的意义 (常考简答)**
    *   问：为什么不直接用 MSI 协议，非要加个 E？
    *   答：为了**优化私有数据的写操作**。如果没有 E，读取数据后状态为 S，若紧接着要写，必须发 Invalidate 消息。有了 E，读取后状态为 E，写操作可以直接本地进行（Silent Upgrade），**减少了总线流量 (Reduce Bus Traffic)**。

2.  **M 到 S 的转换**
    *   只有在**其他 Core 发生 Read Miss** 且**命中你的 M 块**时发生。这意味着数据不再独占，必须共享，且必须把脏数据同步回主存（或更新给请求者）。

3.  **S 到 M 的转换**
    *   这是**Write Hit**的情况，必须发 **Invalidate**。

4.  **I 到 M 的转换**
    *   这是**Write Miss**的情况，必须发 **RWITM**。

5.  **总线事务 RWITM 是什么？**
    *   它是 Read Miss 和 Invalidate 的组合。意思是：“我要读这个块（因为我没有），而且我读它是为了马上修改它，所以你们把副本都扔了吧。”

####  考试常见题型预测
*   **状态填空**：给出一个 Core 1 读 -> Core 2 读 -> Core 1 写 -> Core 2 写的序列，让你填每一步之后各个 Core 的 Cache 状态（M/E/S/I）。
*   **画图题**：画出 MESI 的状态转换图（Slide 16 的那个圆圈图，建议背下来）。
*   **分析题**：如果 Core A 处于 S 状态，想写数据，总线上会发生什么？（答：广播 Invalidate，A 变 M，其他人变 I）。

### 第四部分：目录一致性协议 (Directory Coherence Protocols)

#### 1. 为什么要引入目录协议？
**（Slide 32）**

*   **Snooping 协议的瓶颈**：
    *   Snooping 依赖于**广播 (Broadcast)** 机制。
    *   **总线 (Bus)** 是共享资源，带宽有限。随着核心数量增加，总线上的流量（Traffic）会迅速饱和，导致严重的性能瓶颈。
    *   **结论**：Snooping 协议**扩展性差 (Poor Scalability)**，仅适用于小规模多核系统。

*   **目录协议的优势**：
    *   **避免广播**：通过引入一个“目录 (Directory)”结构，记录谁拥有该数据块的副本。
    *   **点对点通信 (Point-to-Point)**：当需要一致性操作时，只需要向“持有副本的特定 Core”发送消息，而不是向全网广播。
    *   **适应性**：可以运行在任何互连网络（Interconnection Network, 如 Mesh, Torus）上，不依赖总线，因此具有**更好的扩展性**，适用于大规模（Large-scale）系统。

#### 2. 基本方案：Censier & Feautrier
**（Slide 33 - 核心机制）**

这是一个经典的目录协议实现方案，考试常考其硬件结构和操作流程。

**A. 硬件扩展**
*   **在内存侧 (Main Memory / Directory)**：
    *   对每一个 Memory Block，增加一个目录条目。
    *   **Presence Bits (存在位)**：假设有 $k$ 个处理器，就需要 $k$ 个 bit。第 $i$ 位为 1 表示 Core $i$ 缓存了该块。
    *   **Dirty Bit (脏位)**：1 bit。表示该块是否被某个 Core 独占修改（Modified）。
*   **在缓存侧 (Cache)**：
    *   标准的 Valid bit 和 Dirty (Owner) bit。

**B. 操作流程 (重点理解与 Snooping 的区别)**

1.  **读操作 (Read from Main Memory)**：
    *   Core $i$ 发起读请求。
    *   **若 Directory Dirty-bit is OFF**：
        *   直接从内存读数据。
        *   Directory 将 Presence Bit $[i]$ 置为 1（记录 Core $i$ 有副本）。
    *   **若 Directory Dirty-bit is ON**：
        *   Directory 查表知道是哪个 Core（假设是 Core $j$）持有脏数据。
        *   Directory 命令 Core $j$ 把数据写回/转为 Shared。
        *   更新内存，Dirty-bit 置 OFF，Presence Bit $[i]$ 和 $[j]$ 都置为 1。
        *   将数据返回给 Core $i$。

2.  **写操作 (Write to Main Memory)**：
    *   Core $i$ 发起写请求。
    *   **若 Directory Dirty-bit is OFF**：
        *   Directory 检查 Presence Bits，**只向那些位为 1 的 Core 发送 Invalidate 消息**（这是与 Snooping 的最大区别，不是广播）。
        *   等待确认。
        *   Directory 将 Dirty-bit 置 ON，且只保留 Presence Bit $[i]$ 为 1。

#### 3. 目录协议面临的挑战
**（Slide 34）**

虽然解决了总线带宽问题，但目录协议也有自己的代价：

*   **存储开销 (Storage Overhead)**：
    *   这是最大的问题。
    *   对于每个内存块，都需要维持一个与之对应的目录项。
    *   **不具备扩展性 (Not scale well)**：如果系统有 1024 个 Core，那么**每个**内存块都需要额外的 1024 bits (Presence bits) 来记录状态。这个开销随着 Core 数量线性（甚至超线性）增长，非常浪费内存。
*   **性能瓶颈**：
    *   如果 Directory 是集中的（Centralized），它自己会成为新的热点瓶颈。
    *   **解决方案**：需要使用**分布式目录 (Distributed Directory)**，将目录信息分散存储在不同的节点上。

#### 三、 简答题
1.  **答案**：
    即使使用写直达（Write-through）策略将新数据更新到了主存，但其他 Core 的私有缓存中可能仍然保留着该数据的旧副本（Valid 状态）。当其他 Core 读取该数据时，会直接命中（Hit）自己的本地缓存，读取到旧值，而不会去访问已更新的主存。因此，必须有一种机制（如 Invalid）通知其他 Core 副本已失效。(Slide 5, 6)

2.  **答案**：
    Write Invalidate 更节省带宽。
    (1) **多字写入 (Multi-word writes)**：对于同一个 Cache Block 的多个 Words 的写入，Write Invalidate 只需要发一次失效消息即可获得独占权，后续写入在本地进行；而 Write Update 需要对每个 Word 的改变都广播一次。
    (2) **局部性 (Locality)**：程序通常在短时间内多次修改同一变量。Write Invalidate 只有第一次需要总线交互，后续利用本地缓存；Write Update 每次都要广播。(Slide 12)

3.  **答案**：
    **目的**：E 状态表示“独占且干净”。
    **优化**：在 MSI 协议中，读入数据通常为 S 状态。如果随后要进行写操作，必须发送 Invalidate 消息将 S 变为 M。而在 MESI 中，如果是 E 状态（已知独占），由 E 变为 M 是静默的（Silent Upgrade），**不需要在总线上发送任何信号**，从而显著减少了总线流量（Bus Traffic）。(Slide 16, 23)

#### 四、 综合分析题

**1. MESI 状态图**
*(参考 Slide 30)*
*   I -> E (Read Miss, no sharers)
*   I -> S (Read Miss, sharers exist)
*   E -> M (Write Hit, silent)
*   S -> M (Write Hit, send Invalidate)
*   I -> M (Write Miss, send RWITM)
*   M -> M, E -> E, S -> S (Read Hit)

**2. 状态追踪分析**

| 步骤  | 操作行为       | Core 0    | Core 1    | Core 2     | 总线事务             | 解析                                                |
| :-- | :--------- | :-------- | :-------- | :--------- | :--------------- | :------------------------------------------------ |
| 1   | Core 0 读 X | **(1) E** | I         | I          | **(2) Mem Read** | C0 读缺失，其他核无副本，状态置为 E (独占)。                        |
| 2   | Core 1 读 X | **(3) S** | **(4) S** | I          | Mem Read         | C1 读缺失，C0 监听到后，将 E 降级为 S，C1 变为 S。                 |
| 3   | Core 2 写 X | **(5) I** | **(6) I** | **(7) M**  | **(8) RWITM**    | C2 写缺失，发送 RWITM。C0, C1 看到后变为 Invalid。C2 变为 M。     |
| 4   | Core 0 读 X | **(9) S** | I         | **(10) S** | Mem Read + Flush | C0 读缺失。C2 处于 M，需先将脏数据写回 (Flush)，C2 降级为 S，C0 变为 S。 |

**3. 目录协议分析**
1.  **状态**：Shared (因为 Dirty bit 是 0)。**副本持有者**：P0 和 P1。(Slide 33)
2.  **P2 写操作步骤**：
    *   Directory 检测到 Dirty bit 为 OFF。
    *   Directory 根据 Presence bits，向 **P0** 和 **P1** 发送 **Invalidation** 消息（而不是广播）。
    *   等待 P0 和 P1 确认失效。
    *   Directory 将 **Dirty bit 置为 1 (ON)**。
    *   Directory 更新 Presence bits：**只保留 P2 为 1** (即 0 0 1)。
    *   允许 P2 写入。 (Slide 33)
